## 2. 关系表设计

### 2.1 user 用户（老人 + 监护人，含角色）

```sql
CREATE TABLE "user" (
    id             BIGSERIAL PRIMARY KEY,
    user_id        VARCHAR(64)  NOT NULL UNIQUE,        -- 业务ID
    username       VARCHAR(64)  UNIQUE,                 -- 登录账号（可空，手机号亦可直接登录）
    password_hash  VARCHAR(100) NOT NULL,               -- BCrypt 加盐**单向哈希**（不是加密），永不存明文
    name           VARCHAR(64),
    phone          VARCHAR(20)  UNIQUE,                 -- 登录账号（与 username 二选一）
    role           VARCHAR(16)  NOT NULL,               -- ELDER 老人 / GUARDIAN 监护人 / ADMIN 管理员（测试数据清理，见 V11）
    wechat_open_id VARCHAR(64) UNIQUE,                  -- 【暂不使用】预留，接入微信登录时启用
    status         VARCHAR(16) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE 正常 / DELETED 已注销（V7 新增，见下方《账号注销》）
    deleted_at     TIMESTAMPTZ,                         -- 注销时间，status='DELETED' 时非空（V7 新增）
    created_at     TIMESTAMPTZ DEFAULT NOW()
);
```

> **账号注销（V7，`feat/backend-user-delete`，接口口径见 02 的 3.1）**：注销是**软删除，不删行** ——
> ① `status='DELETED'` + `deleted_at=now()`；② **`phone` / `username` 置 `NULL`** 释放唯一键（`NULL` 不参与唯一约束，故同一手机号可重新注册，注销后原登录标识不再留库）；
> ③ 该用户的 `refresh_token` 全部置 `REVOKED`（见 2.13）；④ 该用户作为 `elder_id` / `guardian_id` 的监护关系**双向**置 `REVOKED`（见 2.2）。
> **业务数据（设备 / 药品 / 计划 / 记录 / 告警 / 抓拍等）一律不级联删除** —— 用药记录需留痕，且保留 `user` 行才能让历史记录里引用的 `user_id` 继续成立。
> 副作用是"已注销的 `user_id` 仍被历史数据引用"，这是**有意为之**：它让软删除与数据留痕同时成立，代价只是没人能再访问到它。
>
> **不拦旧 access token**：注销后已签发的 access 最长 2 小时仍可用（JWT 无状态、不引入黑名单），靠 refresh 已全部撤销兜底；`AuthInterceptor` **不查本表**（否则每个请求都要多一次 `user` 查询）。判定 `DELETED` 的三处是 `AuthService.login`（40102）、`AuthService.refresh`（40101）、`UserService.me`（40101）。

### 2.2 guardian_relation 老人↔监护人绑定

```sql
CREATE TABLE guardian_relation (
    id          BIGSERIAL PRIMARY KEY,
    relation_id VARCHAR(64)  UNIQUE,   -- 业务ID，如 r-1001（V4__authz.sql 新增）
    elder_id    VARCHAR(64) NOT NULL,   -- -> user.user_id (ELDER)
    guardian_id VARCHAR(64) NOT NULL,   -- -> user.user_id (GUARDIAN)
    role        VARCHAR(16),            -- FAMILY 家属 / DOCTOR 医生 / NURSE 护理（可空，判定时兜底 FAMILY）
    status      VARCHAR(16) NOT NULL,   -- PENDING 监护人已申请待老人确认 / ACTIVE 已生效 / REVOKED 已解除
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (elder_id, guardian_id)
);
```

> **`relation_id`（V4 新增）**：与 `user.user_id` / `med_plan.plan_id` 等业务号同风格，供 `PATCH /users/guardians/{relationId}/accept` 与
> `DELETE /users/guardians/{relationId}` 直接使用（P1 `feat/guardian-relation`）。
> `V4__authz.sql` 同时建了 `guardian_relation_biz_id_seq` 序列与 `idx_guardian_relation_guardian` / `idx_guardian_relation_elder` 索引
> （反向查询"我监护了哪些老人"与带 `status` 的正向查询）。
> **命名坑（与 2.13 同类）**：序列不能叫 `guardian_relation_id_seq` —— 那是本表 `id BIGSERIAL` 自动创建的序列，
> 同名会被 `IF NOT EXISTS` 静默跳过、取到自增主键的值（第一条关系变成 `r-1`）。统一用 `_biz_id_seq` 后缀。

> **两步生效**：监护人发起申请 → `PENDING`；老人端确认 → `ACTIVE`。监护人对该老人的读写权限**仅在 `ACTIVE` 期间有效**，`PENDING` 期间访问返回 40302。
>
> **用户注销时的处理（V7）**：账号注销会把该用户作为 `elder_id` **或** `guardian_id` 的全部 `PENDING` / `ACTIVE` 关系置 **`REVOKED`**（双向）。
> 因此"老人注销"表现为监护人的老人列表里该老人消失，"监护人注销"只影响他自己那几条关系、老人与其他监护人不受影响。
> `UNIQUE (elder_id, guardian_id)` 保持不变 —— 重新注册会拿到新的 `user_id`，不会撞上旧组合。

### 2.3 device 设备（药箱主控 + 传感器子设备）

> **一个药箱 = 一个主设备（`MAIN`），其下挂若干传感器子设备**（温湿度、光照、摄像头等），都登记在本表，用 `device_type` 区分、`parent_device_id` 指向所属药箱。**药箱不再划分仓位 / 格子**，药品按"药箱 + 药品"维度管理（见 2.5）。

```sql
CREATE TABLE device (
    id              BIGSERIAL PRIMARY KEY,
    device_id       VARCHAR(64) NOT NULL UNIQUE,
    device_type     VARCHAR(24) NOT NULL,        -- MAIN 药箱主控 / TEMP_HUMI 温湿度 / LIGHT 光照 / CAMERA 摄像头
    parent_device_id VARCHAR(64),                -- 子设备指向所属药箱（MAIN 的 device_id）；主控为空
    product_key     VARCHAR(64),
    secret          VARCHAR(128),                -- 设备凭据（**预留，本期不使用**；当前 EMQX 为匿名连接，见文档 03 第 1 章）
    elder_id        VARCHAR(64),                 -- -> user.user_id (ELDER)。**子设备也填**，与父设备一致，便于行级权限与按老人查询
    timezone        VARCHAR(32) DEFAULT 'Asia/Shanghai',  -- 设备本地时区（服药时间按此换算）
    online_state    VARCHAR(16) DEFAULT 'OFFLINE',-- ONLINE / OFFLINE
    last_heartbeat  TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

**在线状态怎么来**：

- **主控（`MAIN`）**：唯一 MQTT 连接，靠 **MQTT 遗嘱 + KeepAlive** 判定；
- **传感器子设备**：没有 MQTT 连接、也没有遗嘱，由主控通过 `up/sensor/heartbeat` **每 60s** 汇总上报（见文档 03 第 3 章），后端据此更新各子设备的 `last_heartbeat` 与 `online_state`。**连续 3 个周期（180s）未上报即判离线**，子设备超时**不生成 DEVICE_OFFLINE 告警**，仅在设备详情与 `DEVICE_STATUS` 推送中标注。

> **本期不做设备认证**：EMQX 保持匿名连接，`device.secret` 仅作**预留字段、暂不使用**，因此也不涉及加密存储。将来需要时按两级加固 —— ① 关闭匿名 + 共用用户名密码 + `clientId` 白名单 + ACL；② 一机一密（每台设备独立凭据 + HTTP 认证 / 动态签名 / ACL）—— 再考虑凭据的加密存储与密钥分离（见文档 01 附录）。

CREATE TABLE medicine (

### 2.5 medicine_stock 库存（药箱 + 药品维度，不划分仓位）

> **药箱不再划分格子 / 仓位**，药品直接按"哪个药箱里的哪种药"管理：数量、生产日期、有效期都挂在这条记录上。

```sql
CREATE TABLE medicine_stock (
    id              BIGSERIAL PRIMARY KEY,
    stock_id        VARCHAR(64) NOT NULL UNIQUE,
    device_id       VARCHAR(64) NOT NULL,   -- -> device.device_id（药箱 MAIN）
    elder_id        VARCHAR(64),            -- 冗余：-> user.user_id (ELDER)
    medicine_id     VARCHAR(64) NOT NULL,   -- -> medicine.medicine_id
    quantity        INT         DEFAULT 0,  -- 库存数量
    production_date DATE,                   -- 生产日期（监护人手动录入）
    expiry_date     DATE,                   -- 有效期至（监护人手动录入，过期判定唯一依据）
    updated_at      TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (device_id, medicine_id)
);

> **过期判定不做自动识别**：系统不读取任何标签 / RFID，也不做图像识别有效期。`production_date` 与 `expiry_date` 由监护人在**录入 / 补药入库时手动填写**，后端定时按 `expiry_date` 扫描生成临期预警与 EXPIRED 告警。

> **库存扣减的两个来源，避免双重扣减（2026-10-23 口径）**：① 服药事件 `up/event/dispense` 由 `feat/dispense-consume` 按"识别到的药品"扣（`MedicineStockMapper.deduct`，不足扣到 0，见 2.7 规则表 5）；② 设备侧 `up/inventory` 上报的 `quantity` / `delta` 由 P1 `feat/inventory-consume` 消费。**后者只按 `quantity`（变更后库存）做绝对值校准覆盖，不做 delta 累加**——否则会与 ① 重复扣减。即：`dispense` 是权威业务扣减，`inventory` 仅用于校准物理盘点偏差。

#### 说明：传感器子设备与遥测归属

传感器是药箱下的**子设备**，但**只有主控建立 MQTT 连接**，遥测消息中带 `sensorId` 标明来源：

- `env_sample.device_id` 记**传感器**自身的 `device_id`（便于按传感器查曲线、看单个传感器是否掉线）；
- `env_sample.gateway_device_id` 记实际建连上报的主控（便于排障与归属判定）。

因此"某个温湿度传感器离线"由后端按其 `last_heartbeat` 判定，而不是靠 MQTT 连接断开来判断。

### 2.6 med_plan 服药计划（计划头：一次提醒 = 一个计划）

> **一次服药常含多种药**（如降压药 + 阿司匹林同时服用），因此采用**主子表**：计划头描述"什么时间吃"，明细描述"吃哪些药、各吃多少"。**药箱不划分仓位**，因此明细里没有仓位字段，是否拿对药由摄像头识别药品来判定（见文档 01 的 5.2）。

```sql
CREATE TABLE med_plan (
    id                  BIGSERIAL PRIMARY KEY,
    plan_id             VARCHAR(64) NOT NULL UNIQUE,
    elder_id            VARCHAR(64) NOT NULL,   -- -> user.user_id (ELDER)
    name                VARCHAR(64),            -- 方案名，如"早餐后""睡前"（便于老人端区分）
    times               JSONB NOT NULL,          -- ["08:00","20:00"] **设备本地墙钟时间**，时区取 device.timezone
    repeat_rule         VARCHAR(16),             -- DAILY / WEEKLY ...
    miss_alarm_after_min INT,                    -- 漏服容忍(分钟)，可空；见下方优先级
    alarm_rule          JSONB,                    -- {miss,wrongDrug,expired,env}
    status              VARCHAR(16) DEFAULT 'ENABLED',
    sync_state          VARCHAR(16) DEFAULT 'PENDING', -- 下发状态，见下方《计划下发状态》
    created_at          TIMESTAMPTZ DEFAULT NOW()
);
```

> **`sync_state`（V9，`feat/plan-core` 新增）**：02 §6 的响应要回显 `syncState`（如 `SYNCED_TO_DEVICE`），但本建表语句原本漏了这列 —— 由 `V9__plan.sql` 的 `ALTER TABLE med_plan ADD COLUMN` 补上（默认 `PENDING`）。`feat/plan-core` 只负责把计划落库并置 `PENDING`；真正的 `SYNCED_TO_DEVICE` / `SYNC_FAILED` 状态机由后续 `feat/plan-sync`（下发到药箱）接管。**注意**：`med_plan` / `med_plan_item` 两张表由 V1 创建，`V9` 只新增序列（`med_plan_biz_id_seq` / `med_plan_item_biz_id_seq`）、本列与 `idx_plan_elder` 索引，绝不改 V1~V8（Flyway `validate-on-migrate` 会拒改历史迁移）。

### 2.6.1 med_plan_item 服药计划明细（支持一次多种药）

```sql
CREATE TABLE med_plan_item (
    id           BIGSERIAL PRIMARY KEY,
    item_id      VARCHAR(64) NOT NULL UNIQUE,
    plan_id      VARCHAR(64) NOT NULL,   -- -> med_plan.plan_id
    medicine_id  VARCHAR(64) NOT NULL,   -- -> medicine.medicine_id
    dose         VARCHAR(32),            -- 单次剂量，如 "1"
    unit         VARCHAR(16),            -- 片/粒/ml...
    note         VARCHAR(64),            -- 服用说明，如"餐后""嚼服"（可空）
    sort_order   INT DEFAULT 0,          -- 展示顺序
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_plan_item_plan ON med_plan_item (plan_id);
```

**完整性约束（应用层保证）**：

- 同一 `plan_id` 下的 `medicine_id` 不重复（一种药在同一个计划里只出现一次）；
- 计划中的药品必须在该药箱 `medicine_stock` 里有库存且未过期，否则创建计划时拒绝（40901）；
- 删除计划时级联删除其明细。

**漏服判定口径**：同一 `plan` 的同一 `time` 下，**所有 item 都有对应 `med_record`** 才算本次服药完成；**任一 item 缺失即判定 MISS**，告警 `message` 中列出缺哪几种药。

**漏服容忍时长优先级**：`med_plan.miss_alarm_after_min`（计划级）**>** `alarm_setting.miss_tolerate_min`（老人级）**>** 系统默认 **15 分钟**。计划级留空表示沿用上一级。

**服药时间的时区口径**：`med_plan.times` 存的是**设备本地墙钟时间**（如 `"08:00"`），时区由 `device.timezone` 决定（默认 `Asia/Shanghai`）。服务端判定时把"今天日期 + 该本地时间"按 `device.timezone` 换算成 UTC 后再与上报时间比较；跨天 / 计划修改当日生效等边界由服务端定时任务统一处理。除此之外，所有时间字段（`created_at`、`actual_time`、`sample_time` 等）一律存 **UTC**。

### 2.6.x plan_reminder 服药提醒去重账本（feat/plan-reminder）

> **为什么单独一张表**：REMINDER 不是告警（不进 `alarm` 列表），只是"定时扫描把每个服药槽只提醒一次"的去重账本。设备本地声光提醒为主、云端 WS 提醒是监护端兜底；去重保证服务重启 / 重扫同一窗口不重复推帧。

```sql
CREATE TABLE plan_reminder (
    id          BIGSERIAL PRIMARY KEY,

**去重口径**：`dedup_key = REMINDER:{planId}:{slotUTC}`（slotUTC 为计划槽的 UTC 瞬时，如 `2026-10-22T16:00:00Z`）；落库时若命中 `dedup_key` 唯一约束冲突 → 跳过（不重复推送）。其余判定与 `med_plan` / `med_record` 的关系见 2.6.1 与下方 🧭 规则表。

#### 🧭 判定规则表（feat/plan-reminder，沉淀自 07 清单；2026-10-25）

**1 · 扫描触发（仅定时）**：`@Scheduled` 每 `medbox.plan-reminder.scan-interval-ms`（默认 60000ms）扫一次；窗口 `[now, now + lead-time-minutes]`（默认 10min），只对未来 slot 提醒（已过槽归 `feat/miss-alarm`）。

**2 · 候选计划**：只查 `status = 'ENABLED' AND sync_state <> 'SYNC_FAILED'`（`MedPlanMapper.selectDueForReminder`，与漏服同口径）；`sync_state = PENDING`（未跑同步的测试/演示数据）**仍提醒**。

**3 · 槽展开**：`PlanSlotResolver` 在窗口内、按设备时区（`device.timezone`，缺省 `Asia/Shanghai`）展开 `times` 候选槽（未来 slot）。

**4 · 两道拦截**：
- ① 已服跳过：`MedRecordMapper.countTaken(planId, slotUTC)` 该槽已有 `med_record`（`plan_time` = slot 瞬时）→ 已吃过不提醒；
- ② 去重：`plan_reminder` 插入 `dedup_key` 命中唯一约束冲突 → 跳过；扫描间隔 < 提前量时靠去重保证每 slot 只推一次。

**5 · 组装与推送**：取该计划全部 `med_plan_item`，逐条 → `{itemId, medicineId, medicineName(查 medicine 表), dose, unit}`；`planTime = slot.toInstant()` 的 ISO UTC；经 `WsPushService` 推 `WsFrameType.REMINDER` 到 `elder:{elderId}`。`medbox.plan-reminder.enabled = false` → 整个扫描不跑（逃生开关）。

**6 · 边界**：设备本地为准、云端只兜底——**默认不要求设备在线**（`skip-when-device-offline` 默认 false，可配）；`times` 非法 → 跳过该槽；无 MAIN 设备用默认时区；全程兜异常，单条计划出错不影响其余；WS 未启用/异常静默跳过。

#### 🧭 判定规则表（feat/dispense-consume，沉淀自 07 清单；2026-10-23）

**1 · 消息准入（不通过 → warn 丢弃，不落库）**

| 序 | 条件 | 结果 |
| --- | --- | --- |
| ① | payload JSON 非法 | 丢弃 |
| ② | `planId` 或 `planItemId` 为空 | 丢弃 |
| ③ | 按 topic 解析的 `deviceId` 查不到 `device`，或 `device.elder_id` 为空 | 丢弃 |
| ④ | `plan` 不存在 | 丢弃 |
| ⑤ | `plan.elder_id` ≠ `device.elder_id` | 丢弃（防跨老人伪造） |
| ⑥ | `planItem` 不存在，或 `planItem.plan_id` ≠ payload 的 `planId` | 丢弃 |

补充：`plan.status = DISABLED` **仍落记录**（服药事实已发生）；`ts` 缺失（null 或 ≤0）时用 `clock.instant()`；`ts` 为 epoch **毫秒**。

**2 · `plan_time` 就近槽匹配**：取 `ts` 在 `device.timezone`（缺省 `Asia/Shanghai`）下的本地日期 D，生成 **D-1 / D / D+1 三天** × 全部 `times` 的候选槽，取 `|ts − slot|` 最小者为 `plan_time`（差值相同取较早槽）；`times` 为空 → `plan_time = NULL`、`on_time = NULL`。

**3 · 容忍时长 `resolveToleranceMinutes`（三级，§2.6.1）**：计划级 `med_plan.miss_alarm_after_min` > 老人级 `alarm_setting.miss_tolerate_min` > 系统默认 **15** 分钟（非空且 >0 才生效，否则下探；老人级无配置行 → 默认）。

**4 · `on_time`（单侧窗口，提前恒为 true，只判迟到）**：`plan_time` 为 NULL → NULL；`actual_time ≤ plan_time + 容忍` → true；`>` → false。

**5 · 库存扣减**：写记录成功后，**同一事务内**按 `device_id = 上报主控` 且 `medicine_id = 识别到的药品`（错服时也扣——药确实被拿走）扣；数量取 `parse(actualDose)`，失败或非正数 → **1**；`GREATEST(quantity − delta, 0)` 不足扣到 0（**不阻断写记录**），无库存行（影响行数 0）→ warn；幂等命中时随事务回滚不扣。

**6 · 幂等（两层）**：① `MqttInboundGateway` + `mqtt_message.msg_id` UNIQUE（网关已完成，本分支不重复做）——冲突网关直接丢弃；② `uk_med_record_item_plan_time` 部分唯一索引——冲突捕获后 `setRollbackOnly()` 并 INFO 返回，记录与库存都不写。

**7 · 领域事件**：落库成功后（`@TransactionalEventListener(AFTER_COMMIT)`）发布 `DispenseRecordedEvent`，供 `feat/miss-alarm`（按 `planId`/`planTime`/`planItemId` 判缺服）与 `feat/wrong-drug-alarm`（P1，后端按 `planItemId` 查计划药品、与上报 `medicineId` **比对重算**判定错服，生成 WRONG_DRUG 告警并回写 `med_record.wrong_drug`）消费；本分支**不推 WebSocket、不生成任何告警、不提供 REST**（归 `record-core` / `miss-alarm`）。事件携带 `recordId/elderId/planId/planItemId/medicineId/planTime/actualTime/onTime/wrongDrug/confidence/deviceId/captureId`。

```

> **`alarm_id`（V12 新增序列 `alarm_biz_id_seq`，`START 1001`）**：业务号前缀用 **`a-`**（如 `a-1001`）——
> 命名切忌 `alarm_id_seq`：那是 `alarm.id BIGSERIAL` 自动创建的序列，复用会取到自增主键值（同 `med_record_biz_id_seq` / `med_plan_biz_id_seq` 同一个坑，`V12__miss_alarm.sql` 用 `IF NOT EXISTS` 兜底）。

> **`dedup_key`（V12 新增）**：告警去重键，让"定时扫描重复扫到同一已判定槽"不产生重复告警。取值约定：
> - `MISS` = `MISS:{planId}:{slotUTC}`（slotUTC 为计划槽的 UTC 瞬时，如 `2026-10-22T16:00:00Z`）；
> - `WRONG_DRUG` = `WRONG_DRUG:{recordId}`（`feat/wrong-drug-alarm` 事件驱动，每条服药记录最多一条错服告警）；
> - 后续 `ENV` / `DEVICE_OFFLINE` / `DEVICE_FAULT` 等复用同一列（各自前缀），统一收敛告警去重逻辑。
> 落库时若命中 `uk_alarm_dedup_key` 唯一索引冲突 → 跳过（不重复落库、不重复推 WS）。

#### 🧭 判定规则表（feat/miss-alarm，沉淀自 07 清单 P0 第 10 步；2026-10-23）

**1 · 扫描触发（仅定时，符合 01 §5.1 口径）**：`@Scheduled` 每 `medbox.alarm.miss.scan-interval-ms`（默认 60000ms）扫一次，**不消费 `DispenseRecordedEvent` 做事件驱动即时判定**（该事件仅预留）；扫描窗口 `[now - lookback(默认 1440min), now - tolerance]`，`tolerance` = 三级容忍（§2.6.1，计划级 > 老人级 > 系统 15min）。

**2 · 候选计划（跳过规则，用户确认）**：只查 `status = 'ENABLED' AND sync_state <> 'SYNC_FAILED'`（`MedPlanMapper.selectDueForMissScan`）；
`status != ENABLED` 不判（由查询过滤）；`sync_state = SYNC_FAILED` 跳过（设备没收到计划不会提醒）；`sync_state = PENDING`（未跑同步的测试/演示数据）**仍判**（否则永远看不到告警）。
`medbox.alarm.miss.skip-when-device-offline = true`（默认）时，该老人 **MAIN 主控 `online_state != ONLINE`** 跳过，避免"上报不了 = 漏服"误判。

**3 · 槽展开**：用公共组件 `PlanSlotResolver`（由 `dispense-consume` 的"就近槽"抽出，共用同一套"本地墙钟 `times` → 具体瞬时"换算）：在窗口内、按设备时区（`device.timezone`，缺省 `Asia/Shanghai`）展开全部 `times` 候选槽。

**4 · 记录比对**：一次拉取该计划在窗口内的全部 `med_record`（用 `idx_med_record_plan_time`），按 `plan_time` 的**瞬时**（`toInstant()`，因落库后 PG 已归一为 UTC）分组，得到每个槽已有的 `plan_item_id` 集合（`source` 为 CAMERA / MANUAL 都算）。

**5 · MISS 判定（一个槽一条告警）**：某槽下，**任一 `med_plan_item` 不在集合内即判 MISS**；生成 **1 条**告警，`message` 列出全部缺失药名（格式 `08:00 计划服药未按时服用：缺 阿莫西林、维生素D`），`alarm.medicine_id` 记**第一个**缺失药，`type = MISS`、`level = WARN`、`plan_id` 记计划、`device_id` 记 MAIN 设备；WS 帧 `medicineIds` 带全部缺失药品（见 02 第 8 章 / 04 第 3 章）。全部 item 都有记录 → 不告警。

**6 · 去重落库**：`dedup_key = MISS:{planId}:{slotUTC}` 落库，命中 `uk_alarm_dedup_key` 冲突 → 捕获后跳过（不二次落库、不二次推 WS）。

**7 · 推送**：落库成功后经 `WsPushService` 唯一出口推 `WsFrameType.ALARM` 到 `elder:{elderId}`（payload 见 04 第 3 章）；`medbox.ws.enabled = false`（`ObjectProvider` 取不到实例）或推送异常 → 静默跳过，不阻断扫描；全程兜异常，单条计划出错不影响其余计划。

**8 · 边界**：`times` 非法字符串 → 跳过该槽；无 MAIN 设备当离线处理；`medbox.alarm.miss.enabled = false` → 整个扫描不跑（逃生开关）。**本分支不提供 REST**（02 第 8 章的列表/已读/处理与阈值配置归 `feat/alarm-core`）。

#### 🧭 WRONG_DRUG 判定规则表（feat/wrong-drug-alarm，沉淀自 07 清单 P1；2026-10-25）

**0 · 触发（事件驱动，非定时）**：`@TransactionalEventListener(AFTER_COMMIT)` 消费 `DispenseRecordedEvent`（由 `dispense-consume` 落库后派发）；无定时全表扫。`medbox.alarm.wrong-drug.enabled = false` → **整体跳过**（逃生开关）。

**1 · 判定口径（后端权威，用户确认）**：按事件 `planItemId` 查 `med_plan_item` 得**计划药品**，与事件上报 `medicineId`（实际拿的药）比对，不一致即判错服——**不**直接信任设备 `wrongDrug` 标志（与 onTime 的"后端权威"一致）。

**2 · 低置信度不判错服（用户确认）**：事件 `confidence` 存在且 `< medbox.alarm.wrong-drug.confidence-threshold`（默认 0.6）时，**不判错服**，仅当 `captureId` 非空把关联抓拍 `capture.reason` 标记为 `LOW_CONFIDENCE`（交人工复核，行不存在则 0 影响、安全）；无 `captureId` 仅跳过。

**3 · 无法判定不动作**：实际 `medicineId` 为空，或计划药缺失（`med_plan_item` 查不到 / 计划药为空）→ 不告警、不标记、不回写。

**4 · 正确服药**：实际药 == 计划药 → 回写 `med_record.wrong_drug = false`，**不告警**。

**5 · 错服告警**：实际药 != 计划药 → ① 回写 `med_record.wrong_drug = true`；② 生成 1 条告警 `type = WRONG_DRUG`、`level = CRITICAL`（用户确认，用药安全事故最高优先级）、`medicine_id = 实际药`、`message = "错服：本应服用 {计划药名}，实际服用 {实际药名}"`、`plan_id`/`device_id` 取自事件、`dedup_key = WRONG_DRUG:{recordId}`；③ 落库后经 `WsPushService` 唯一出口推 `WsFrameType.ALARM` 到 `elder:{elderId}`（payload 见 04 第 3 章）。

**6 · 去重**：落库时命中 `uk_alarm_dedup_key` 唯一索引冲突（`DuplicateKeyException`）→ 跳过，不重复落库、不重复推 WS。

**7 · 边界**：`confidence == null` 不触发低置信判定、仍按药品比对；设备离线不适用（事件到达即代表设备已上报）；错服由实际 `dispense` 事件驱动，与 MISS 不同**不按 `plan.alarm_rule.wrongDrug` 门控**（与 MISS 行为一致）；全程兜异常，单条记录判定失败只记日志不阻断。`capture.reason` 的 `LOW_CONFIDENCE` 由本分支写入，`feat/capture-core` 后续在此扩展其余读写（合并点见 CHANGELOG）。

    api_key_enc  TEXT,                          -- 加密存储的大模型 Key（AES + 密钥与库分离），回显脱敏；**为什么必须加密见文档 01 附录**
    model        VARCHAR(64),
    base_url     VARCHAR(255),
    enabled      BOOLEAN DEFAULT TRUE,
    updated_at   TIMESTAMPTZ DEFAULT NOW()
);
```

### 2.12 capture 设备抓拍图片（摄像头留证，7 天过期）

```sql
CREATE TABLE capture (
    id           BIGSERIAL PRIMARY KEY,
    capture_id   VARCHAR(64) NOT NULL UNIQUE,
    device_id    VARCHAR(64) NOT NULL,   -- -> device.device_id
    elder_id     VARCHAR(64) NOT NULL,   -- -> user.user_id (ELDER)
    medicine_id  VARCHAR(64),            -- 抓拍涉及的药品（可空）
    plan_id      VARCHAR(64),            -- 关联计划（可空）
    reason       VARCHAR(24) NOT NULL,   -- NORMAL 正常服药 / WRONG_DRUG 错服 / LOW_CONFIDENCE 存疑 / MANUAL 主动
                                          -- LOW_CONFIDENCE 由 feat/wrong-drug-alarm 在低置信度识别时写入（交人工复核）；
                                          -- 其余取值的读写归后续 feat/capture-core（合并点见 CHANGELOG）
    file_path    VARCHAR(512) NOT NULL,  -- 服务端本地存储路径，**不对外暴露**
    mime         VARCHAR(32) DEFAULT 'image/jpeg',
    size_bytes   INT,
    confidence   NUMERIC(4,3),           -- 识别置信度（可空）
    captured_at  TIMESTAMPTZ NOT NULL,   -- 抓拍时刻（UTC）
    viewed_at    TIMESTAMPTZ,            -- 首次被监护人查看的时刻（可空=未读）
    expire_at    TIMESTAMPTZ NOT NULL,   -- 清理时刻，按下方规则计算
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_capture_elder_time ON capture (elder_id, captured_at DESC);
CREATE INDEX idx_capture_expire ON capture (expire_at);
```

**存储与过期**：

- 局域网部署不引入对象存储，图片存后端主机本地目录（`medbox.capture.dir`，默认 `/var/medbox/captures/YYYY-MM-DD/`），**只落盘不入库**，`file_path` 不对小程序暴露，一律经 `/captures/{id}/file` 接口鉴权读取。
- **过期规则（已读 / 未读分开算）**：
  - **未读**：`expire_at = captured_at + 30 天`（未读最长保留 30 天）；
  - **已读**：首次查看时写入 `viewed_at`，并把 `expire_at` 重算为 `viewed_at + 7 天`；
  - 两者**取更早的那个**（即查看后只会让过期时间提前，不会延长）：`expire_at = MIN(captured_at + 30d, viewed_at + 7d)`。
  - 天数均可配：`medbox.capture.retention-days-unread`（默认 30）、`medbox.capture.retention-days-read`（默认 7）。后端每日定时任务扫描 `expire_at <= now()`，删除文件与记录；监护人也可手动提前删除。
- **抓拍策略由摄像头侧决定**（不在后端 / 小程序范围内）：**当前是"正常服药也拍、每次服药都拍"的全量抓拍**（`reason=NORMAL` 占绝大多数）。因此存储与过期必须按全量估算：单张约 200KB~1MB，按每天 4 次服药计约 2MB/天/老人，未读 30 天留存约 60MB/老人 —— 部署时务必预留磁盘配额并考虑后续引入边缘节点清洗（见文档 03 第 4 章）。
- **可见范围比默认规则更严格**：仅**老人本人**与其 **ACTIVE 监护人**可读取；护理人员 / 家庭医生不可见（用药图像属敏感健康数据）。

### 2.13 refresh_token 刷新令牌（轮换制，`feat/backend-auth`）

```sql
-- 业务 user_id 生成器：'u-' || nextval('user_biz_id_seq')
-- 名字不能叫 user_id_seq：那是 "user" 表 id BIGSERIAL 自动创建的序列，会撞名
CREATE SEQUENCE user_biz_id_seq START 1001;

CREATE TABLE refresh_token (
    id          BIGSERIAL PRIMARY KEY,
    token_id    VARCHAR(64)  NOT NULL UNIQUE,   -- 与 refresh JWT 的 jti 一致
    user_id     VARCHAR(64)  NOT NULL,          -- -> user.user_id
    token_hash  VARCHAR(128) NOT NULL,          -- refresh token 的 SHA-256，**不存明文**
    status      VARCHAR(16)  NOT NULL,          -- ACTIVE 生效中 / ROTATED 已轮换 / REVOKED 已撤销
    replaced_by VARCHAR(64),                    -- 轮换后接替它的 token_id（REVOKED 时为空）
    expires_at  TIMESTAMPTZ  NOT NULL,          -- 与 JWT 的 exp 一致
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_refresh_token_user ON refresh_token (user_id);
CREATE INDEX idx_refresh_token_expires ON refresh_token (expires_at);
```

**为什么要落库**：文档 02 第 3 章要求"refresh **轮换**：新的 refreshToken 顶替旧的、旧的立即作废"。
纯 JWT 做不到"作废旧令牌"（签名有效期内依然能用），所以服务端必须记住状态 —— 才能支持轮换、登出与重放检测。

- **只存哈希**：`token_hash` 是 token 的 SHA-256，拖库也换不来可用凭据（token 只需要比对、不需要还原，与密码同理，见文档 01 附录）；
- **轮换**：用 refresh token 换新的时，旧行置 `ROTATED` 并由新行回填 `replaced_by`；
- **重放保护**：再次使用已 `ROTATED` / `REVOKED`（或哈希不吻合）的 token，视为令牌可能已泄漏 —— **撤销该用户全部 refresh token** 并返回 40101；
- **账号注销（`feat/backend-user-delete`）**：`POST /users/me/delete` 调 `revokeAll(userId)` 把该用户全部生效中的行置 **`REVOKED`** —— **这是 `REVOKED` 唯一的主动触发点**（重放保护是被动触发）。注销后旧 access token 最长 2 小时仍可用，靠 refresh 已撤销兜底；**注销账号再来 refresh 直接 40101，不再走"重放检测撤销全部"**（该用户已无生效 token，不必再为其写库）；
- **过期**：`expires_at` 到期即不可用（返回 40101），不牵连其它会话；过期记录由清理任务删除。

> `user_biz_id_seq` 是 `user.user_id`（如 `u-1001`）的生成器：用独立序列而不是"插入后按 id 回填"，省掉一次 UPDATE。
> **不能叫 `user_id_seq`** —— 那是 `"user"` 表 `id BIGSERIAL` 自动创建的序列（表名 + 列名 + `_seq`），
> 叫同一个名字会 `IF NOT EXISTS` 静默跳过、然后一直取到自增主键的值（首个用户变成 `u-1`）。

### 2.14 idempotency_record 幂等记录（`X-Request-Id` 去重）

```sql
CREATE TABLE idempotency_record (
    id                BIGSERIAL PRIMARY KEY,
    request_id        VARCHAR(64) NOT NULL,     -- 客户端 X-Request-Id
    endpoint          VARCHAR(64) NOT NULL,     -- 幂等作用域，当前只有 AUTH_REGISTER
    request_hash      VARCHAR(64) NOT NULL,     -- 请求体指纹（不含密码）
    response_snapshot TEXT        NOT NULL,     -- 首次响应的 data 快照（JSON 字符串）
    expires_at        TIMESTAMPTZ NOT NULL,     -- 过期后不再回放
    created_at        TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (request_id, endpoint)
);
CREATE INDEX idx_idempotency_expires ON idempotency_record (expires_at);
```

- **键**是 `(request_id, endpoint)`：同一个 `X-Request-Id` 在不同接口之间互不干扰；命中即回放首次响应，保证"重复提交只生效一次"；
- **同号不同内容**（换了手机号 / 角色却复用同一个号）按 **40001** 处理 —— 那是客户端用错了号；
- **指纹不含密码**：同号重发视为同一次提交（密码不在指纹里，避免"改个密码重发"被误判）；
- **当前只保护 `POST /auth/register`**（`endpoint=AUTH_REGISTER`）：登录 / 刷新天然幂等，不落记录 —— 免得把含 token 的响应快照写进库里；
- **TTL**：`medbox.idempotency.ttl-hours`（默认 24 小时），过期后不再回放，记录由清理任务删除。

### 2.15 mqtt_message MQTT 上行去重（`V5__mqtt.sql` 新增）

```sql
CREATE TABLE mqtt_message (
    id          BIGSERIAL PRIMARY KEY,
    msg_id      VARCHAR(96)  NOT NULL UNIQUE,   -- 上行消息 msgId（**全局唯一**：协议保证它已含 deviceId）
    device_id   VARCHAR(64)  NOT NULL,          -- -> device.device_id（解析自 topic 第 3 层）
    topic       VARCHAR(128) NOT NULL,          -- 完整上行 topic，便于排障
    received_at TIMESTAMPTZ  DEFAULT NOW(),     -- 首次处理时间
    expires_at  TIMESTAMPTZ  NOT NULL           -- 过期后可删除（默认 7 天）
);
CREATE INDEX idx_mqtt_message_expires ON mqtt_message (expires_at);
```

- **为什么需要它**：设备断线重连会重发未完成确认的上行消息（见文档 03 第 1 章），不去重就会**重复写服药记录 / 重复生成告警**；
- **键是 `msg_id`**（格式 `{deviceId}-{10位递增序号}`，协议已保证全局唯一），无需按设备再做联合唯一；
- **用法必须是"先 INSERT 抢唯一键"**，命中冲突即判定重复并丢弃 —— **不能"先查再插"**：并发下两条重复消息可以同时通过 SELECT 检查；
- **与 2.14 的 `idempotency_record` 是两回事**（一个管设备上行、一个管 REST 重复提交）：作用域不同、保留时长也不同，**不要合并**；
- **TTL**：`medbox.mqtt.dedup-retention-days`（默认 7 天），只要覆盖设备的重发窗口；过期记录由清理任务删除。

### 2.16 device_event 设备事件流水（`feat/device-core`）

```sql
CREATE TABLE device_event (
    id          BIGSERIAL PRIMARY KEY,
    device_id   VARCHAR(64)  NOT NULL,          -- -> device.device_id（子设备也直接记自己的编号）
    event_type  VARCHAR(24)  NOT NULL,          -- REGISTERED / ONLINE / OFFLINE / FAULT / COMMAND
    detail      VARCHAR(512),                   -- 事件补充描述（如故障原因），可为空
    created_at  TIMESTAMPTZ  DEFAULT NOW()
);
CREATE INDEX idx_device_event_device_time ON device_event (device_id, created_at DESC);

-- V6 同时给 device 表补两个索引
CREATE INDEX idx_device_elder  ON device (elder_id);
CREATE INDEX idx_device_parent ON device (parent_device_id);
```

**`event_type` 取值与写入方**：

| 取值 | 含义 | 写入分支 |
|------|------|----------|
| `REGISTERED` | 设备登记（主控与其子设备各记一条） | `feat/device-core` |
| `ONLINE` / `OFFLINE` | 主控上线 / 离线（MQTT status 与遗嘱驱动） | `feat/device-core` |
| `FAULT` | 设备侧异常（门超时 / 识别失败 / 硬件故障） | `feat/device-fault`（P1） |
| `COMMAND` | 控制命令下发与回执 | `feat/device-command`（P1） |

**约定**：

- **只有状态真的发生跃变才写 `ONLINE` / `OFFLINE`**：主控每 60s 有心跳，若每次上行都写一条，
  一天就是 1440 条噪声，事件流水会被心跳灌满。判跃变靠更新条件带 `online_state != 目标状态`
  （受影响行数 > 0 才算跃变），兼作天然幂等；
- **子设备记自己的 `device_id`**，不折算成主控 —— 详情页按主控查流水时能看到是哪颗传感器出了事，
  而归属老人还是从 `device.elder_id` 取（子设备的 `elder_id` 与父设备一致，见 2.3）；
- **不复用 `mqtt_message`（2.15）**：那张表是上行消息去重账本，只有 `msg_id` 与 topic、
  没有事件类型语义，且 7 天就过期清理。两者作用域与生命周期都不同，**不要合并**；
- **本表无业务号**：事件只在"某台设备的流水"这个作用域内被引用，列表接口返回自增主键即可；
- **`device` 表补索引的原因**：`idx_device_elder` 服务于设备列表的行级过滤（`elder_id IN (...)`），
  `idx_device_parent` 服务于详情查下属子设备（`parent_device_id = ?`）。
  设备表数据量极小（每老人个位数），建索引是为了避免这两条高频查询退化成全表扫描。

### 3.3 召回检索（带过滤，避免跨药品 / 跨老人召回）

```sql
SELECT chunk_id, medicine_id, content,
       embedding <=> :qvec AS distance
FROM drug_manual_chunk
WHERE medicine_id = :mid
ORDER BY distance
LIMIT 5;
```

约束：`embedding` 维度必须与所选 embedding 模型一致 —— **本地 `bge-m3` 为 1024 维**（若改用其他模型，须同步改维度并**重建全部分块向量**，否则检索结果无意义）；`<=>` 为余弦距离算子；召回尽量带 `medicine_id` / `elder_id` 过滤；分块保留页码 / 块序号 / 来源，便于答案标出处。Spring AI `PgVectorStore` 亦可自动建表（`dimensions=1024`、`distance-type=COSINE_DISTANCE`、`index-type=HNSW`），字段名按框架默认即可，与上表等价。
