# 06 · 数据库设计（PostgreSQL + pgvector）

> 版本见 `CHANGELOG.md`　|　统一存储：结构化关系数据与说明书向量数据同库存放（PostgreSQL 启用 pgvector 扩展），不单独部署向量数据库。
> 命名：表名小写下划线、主键统一 `id BIGSERIAL` 或业务主键、时间统一 `TIMESTAMPTZ`（UTC）。外键关系在注释中标注，是否建物理外键由团队决定。
>
> **落地方式**：本文档的 DDL 由 **Flyway** 管理，脚本在 `medbox-server/src/main/resources/db/migration/`。应用启动时自动执行，空库一键初始化（见文档 01 的 4.1.3）。

## 1. 实体关系总览

```
User(老人/监护人) --1:N-- GuardianRelation --N:1-- User(老人)
User --1:N-- RefreshToken(轮换的 refresh token，只存哈希，见 2.13)
Elder(=User.role=ELDER) --1:N-- Device
Device --1:N-- MedicineStock --N:1-- Medicine   -- 库存按药品管（下层仓储区，后端不建模格子）
Device --1:N-- Device(子设备:温湿度/光照/摄像头传感器)
Device --1:N-- DeviceEvent(登记/上下线/故障/命令流水)
Device --1:N-- DeviceCommand(控制命令下发与回执流水，见 2.17)
Elder  --1:N-- MedPlan --1:N-- MedPlanItem --N:1-- Medicine
MedPlan--1:N-- MedRecord
Device --1:N-- EnvSample
Elder  --1:N-- Alarm ; Elder --1:1-- AlarmSetting ; Elder --1:1-- LlmConfig
Medicine--1:N-- DrugManual --1:N-- DrugManualChunk(pgvector)
```

## 2. 关系表设计

### 2.1 user 用户（老人 + 监护人，含角色）

```sql
CREATE TABLE "user" (
    id             BIGSERIAL PRIMARY KEY,
    user_id        VARCHAR(64)  NOT NULL UNIQUE,        -- 业务ID
    username       VARCHAR(64)  UNIQUE,                 -- 登录账号（可空，手机号亦可直接登录）
    password_hash  VARCHAR(100) NOT NULL,               -- BCrypt 加盐**单向哈希**（不是加密），永不存明文
    name           VARCHAR(64),
    phone          VARCHAR(20)  UNIQUE,                 -- 登录账号（与 username 二选一）
    role           VARCHAR(16)  NOT NULL,               -- ELDER 老人 / GUARDIAN 监护人 / ADMIN 管理员（测试数据清理，见 02 第 10 章）
    wechat_open_id VARCHAR(64) UNIQUE,                  -- 【暂不使用】预留，接入微信登录时启用
    status         VARCHAR(16) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE 正常 / DELETED 已注销
    deleted_at     TIMESTAMPTZ,                         -- 注销时间，status='DELETED' 时非空
    created_at     TIMESTAMPTZ DEFAULT NOW()
);
```

> **账号注销**：注销是**软删除，不删行** ——
> ① `status='DELETED'` + `deleted_at=now()`；② **`phone` / `username` 置 `NULL`** 释放唯一键（`NULL` 不参与唯一约束，故同一手机号可重新注册，注销后原登录标识不再留库）；
> ③ 该用户的 `refresh_token` 全部置 `REVOKED`（见 2.13）；④ 该用户作为 `elder_id` / `guardian_id` 的监护关系**双向**置 `REVOKED`（见 2.2）。
> **业务数据（设备 / 药品 / 计划 / 记录 / 告警 / 抓拍等）一律不级联删除** —— 用药记录需留痕，且保留 `user` 行才能让历史记录里引用的 `user_id` 继续成立。
> 副作用是"已注销的 `user_id` 仍被历史数据引用"，这是**有意为之**：它让软删除与数据留痕同时成立，代价只是没人能再访问到它。
>
> **不拦旧 access token**：注销后已签发的 access 最长 2 小时仍可用（JWT 无状态、不引入黑名单），靠 refresh 已全部撤销兜底；判定 `DELETED` 的三处是 `login`（40102）、`refresh`（40101）、`me`（40101）。注销接口口径见 02 的 3.1。

### 2.2 guardian_relation 老人↔监护人绑定

```sql
CREATE TABLE guardian_relation (
    id          BIGSERIAL PRIMARY KEY,
    relation_id VARCHAR(64)  UNIQUE,   -- 业务ID，如 r-1001
    elder_id    VARCHAR(64) NOT NULL,   -- -> user.user_id (ELDER)
    guardian_id VARCHAR(64) NOT NULL,   -- -> user.user_id (GUARDIAN)
    status      VARCHAR(16) NOT NULL,   -- PENDING 监护人已申请待老人确认 / ACTIVE 已生效 / REVOKED 已解除
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (elder_id, guardian_id)
);
```

> **`relation_id`**：与 `user.user_id` / `med_plan.plan_id` 等业务号同风格，供 `PATCH /users/guardians/{relationId}/accept` 与
> `DELETE /users/guardians/{relationId}` 直接使用。

> **两步生效**：监护人发起申请 → `PENDING`；老人端确认 → `ACTIVE`。监护人对该老人的读写权限**仅在 `ACTIVE` 期间有效**，`PENDING` 期间访问返回 40302。
> 监护人统一为 `GUARDIAN` **单一角色**（不再区分家属 / 医生 / 护理，见文档 10 §1.2），故本表不再保留 `role` 细分列；绑定类型均由 `user.role = GUARDIAN` 表达。
>
> **用户注销时的处理**：账号注销会把该用户作为 `elder_id` **或** `guardian_id` 的全部 `PENDING` / `ACTIVE` 关系置 **`REVOKED`**（双向）。
> 因此"老人注销"表现为监护人的老人列表里该老人消失，"监护人注销"只影响他自己那几条关系、老人与其他监护人不受影响。
> `UNIQUE (elder_id, guardian_id)` 保持不变 —— 重新注册会拿到新的 `user_id`，不会撞上旧组合。

### 2.3 device 设备（药箱主控 + 传感器子设备）

> **一个药箱 = 一个主设备（`MAIN`），其下挂若干传感器子设备**（温湿度、光照、摄像头等），都登记在本表，用 `device_type` 区分、`parent_device_id` 指向所属药箱。**药箱为分层结构**：上层带锁分格（每日用药区）、下层仓储区（库存），后端不建模格子（`cell_id` 不入库），药品库存按"药箱 + 药品"维度管理（见 2.5）。

```sql
CREATE TABLE device (
    id              BIGSERIAL PRIMARY KEY,
    device_id       VARCHAR(64) NOT NULL UNIQUE,
    device_type     VARCHAR(24) NOT NULL,        -- MAIN 药箱主控 / TEMP_HUMI 温湿度 / LIGHT 光照 / CAMERA 摄像头
    parent_device_id VARCHAR(64),                -- 子设备指向所属药箱（MAIN 的 device_id）；主控为空
    product_key     VARCHAR(64),
    secret          VARCHAR(128),                -- 设备凭据（**预留，本期不使用**；当前 EMQX 为匿名连接，见文档 03 第 1 章）
    elder_id        VARCHAR(64),                 -- -> user.user_id (ELDER)。**子设备也填**，与父设备一致，便于行级权限与按老人查询
    timezone        VARCHAR(32) DEFAULT 'Asia/Shanghai',  -- 设备本地时区（服药时间按此换算）
    online_state    VARCHAR(16) DEFAULT 'OFFLINE',-- ONLINE / OFFLINE
    last_heartbeat  TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

**在线状态怎么来**：

- **主控（`MAIN`）**：唯一 MQTT 连接，靠 **MQTT 遗嘱 + KeepAlive** 判定；
- **传感器子设备**：没有 MQTT 连接、也没有遗嘱，由主控通过 `up/sensor/heartbeat` **每 60s** 汇总上报（见文档 03 第 3 章），后端据此更新各子设备的 `last_heartbeat` 与 `online_state`。**连续 3 个周期（180s）未上报即判离线**，子设备超时**不生成 DEVICE_OFFLINE 告警**，仅在设备详情与 `DEVICE_STATUS` 推送中标注。

> **本期不做设备认证**：EMQX 保持匿名连接，`device.secret` 仅作**预留字段、暂不使用**，因此也不涉及加密存储。将来需要时按两级加固 —— ① 关闭匿名 + 共用用户名密码 + `clientId` 白名单 + ACL；② 一机一密（每台设备独立凭据 + HTTP 认证 / 动态签名 / ACL）—— 再考虑凭据的加密存储与密钥分离（见文档 01 附录）。

```sql
CREATE TABLE medicine (

    name             VARCHAR(128) NOT NULL,
```

### 2.5 medicine_stock 库存（药箱 + 药品维度，下层仓储区，后端不建模格子）

> **药箱下层为仓储区**（后端不建模格子），库存药品直接按"哪个药箱里的哪种药"管理：数量、生产日期、有效期都挂在这条记录上。

```sql
CREATE TABLE medicine_stock (
    id              BIGSERIAL PRIMARY KEY,
    stock_id        VARCHAR(64) NOT NULL UNIQUE,
    device_id       VARCHAR(64) NOT NULL,   -- -> device.device_id（药箱 MAIN）
    elder_id        VARCHAR(64),            -- 冗余：-> user.user_id (ELDER)
    medicine_id     VARCHAR(64) NOT NULL,   -- -> medicine.medicine_id
    quantity        INT         DEFAULT 0,  -- 库存数量
    production_date DATE,                   -- 生产日期（监护人手动录入）
    expiry_date     DATE,                   -- 有效期至（监护人手动录入，仅作记录字段，系统不再据其判定/预警过期）
    updated_at      TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (device_id, medicine_id)
);
```

> **过期功能已删除**：系统不读取任何标签 / RFID，也不做图像识别有效期，更不再定时扫描 `expiry_date` 生成临期预警 / EXPIRED 告警。`production_date` 与 `expiry_date` 由监护人在**录入 / 补药入库时手动填写**，仅作记录字段保留，系统不据其判定或预警过期。

> **库存扣减（由后端执行、依摄像头已服事件判定）**：初始库存数量与每次服药应消耗量由**监护人手动录入**；后端据摄像头上报的**已服事件**（识别结论 `TAKEN` / 已服）判定本次是否实际服药，命中则按监护人录入的应消耗量**计算并扣除**当前库存（不足扣到 0，不阻断写记录），**漏服不扣**。设备不再上报库存（`up/inventory` 已删除），故无设备自动校准分支。

#### 说明：传感器子设备与遥测归属

传感器是药箱下的**子设备**，但**只有主控建立 MQTT 连接**，遥测消息中带 `sensorId` 标明来源：

- `env_sample.device_id` 记**传感器**自身的 `device_id`（便于按传感器查曲线、看单个传感器是否掉线）；
- `env_sample.gateway_device_id` 记实际建连上报的主控（便于排障与归属判定）。

因此"某个温湿度传感器离线"由后端按其 `last_heartbeat` 判定，而不是靠 MQTT 连接断开来判断。

### 2.6 med_plan 服药计划（计划头：一次提醒 = 一个计划）

> **一次服药常含多种药**（如降压药 + 阿司匹林同时服用），因此采用**主子表**：计划头描述"什么时间吃"，明细描述"吃哪些药、各吃多少"。**后端不建模格子**（带锁分格是药箱本地物理概念，`cell_id` 不入库），计划只描述"时间 + 药品"，是否服药由摄像头端侧人脸识别结论判定（见文档 01 的 5.2 / 文档 10 §2.1）。

```sql
CREATE TABLE med_plan (
    id                  BIGSERIAL PRIMARY KEY,
    plan_id             VARCHAR(64) NOT NULL UNIQUE,
    elder_id            VARCHAR(64) NOT NULL,   -- -> user.user_id (ELDER)
    name                VARCHAR(64),            -- 方案名，如"早餐后""睡前"（便于老人端区分）
    times               JSONB NOT NULL,          -- ["08:00","20:00"] **设备本地墙钟时间**，时区取 device.timezone
    repeat_rule         VARCHAR(16),             -- DAILY / WEEKLY ...
    miss_alarm_after_min INT,                    -- 漏服容忍(分钟)，可空；见下方优先级
    alarm_rule          JSONB,                    -- {miss,env}
    status              VARCHAR(16) DEFAULT 'ENABLED',
    sync_state          VARCHAR(16) DEFAULT 'PENDING', -- 下发状态，见下方《计划下发状态》
    created_at          TIMESTAMPTZ DEFAULT NOW()
);
```

> **`sync_state`**：02 §6 的响应要回显 `syncState`（如 `SYNCED_TO_DEVICE`）。状态机：`PENDING`（已落库待下发）→ `SYNCED_TO_DEVICE`（设备已确认）→ `SYNC_FAILED`（下发失败 / 超时）。真正的状态跃迁由计划下发逻辑接管，本表只定义列与初始值。

### 2.6.1 med_plan_item 服药计划明细（支持一次多种药）

```sql
CREATE TABLE med_plan_item (
    id           BIGSERIAL PRIMARY KEY,
    item_id      VARCHAR(64) NOT NULL UNIQUE,
    plan_id      VARCHAR(64) NOT NULL,   -- -> med_plan.plan_id
    medicine_id  VARCHAR(64) NOT NULL,   -- -> medicine.medicine_id
    dose         VARCHAR(32),            -- 单次剂量，如 "1"
    unit         VARCHAR(16),            -- 片/粒/ml...
    note         VARCHAR(64),            -- 服用说明，如"餐后""嚼服"（可空）
    sort_order   INT DEFAULT 0,          -- 展示顺序
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_plan_item_plan ON med_plan_item (plan_id);
```

**完整性约束（应用层保证）**：

- 同一 `plan_id` 下的 `medicine_id` 不重复（一种药在同一个计划里只出现一次）；
- 计划中的药品必须在该药箱 `medicine_stock` 里有库存，否则创建计划时拒绝（40901）；
- 删除计划时级联删除其明细。

**漏服判定口径**：同一 `plan` 的同一 `time` 下，**所有 item 都有对应 `med_record`** 才算本次服药完成；**任一 item 缺失即判定 MISS**，告警 `message` 中列出缺哪几种药。

**漏服容忍时长优先级**：`med_plan.miss_alarm_after_min`（计划级）**>** `alarm_setting.miss_tolerate_min`（老人级）**>** 系统默认 **15 分钟**。计划级留空表示沿用上一级。

**服药时间的时区口径**：`med_plan.times` 存的是**设备本地墙钟时间**（如 `"08:00"`），时区由 `device.timezone` 决定（默认 `Asia/Shanghai`）。服务端判定时把"今天日期 + 该本地时间"按 `device.timezone` 换算成 UTC 后再与上报时间比较；跨天 / 计划修改当日生效等边界由服务端定时任务统一处理。除此之外，所有时间字段（`created_at`、`actual_time`、`sample_time` 等）一律存 **UTC**。

### 2.6.x plan_reminder 服药提醒去重账本

> **为什么单独一张表**：REMINDER 不是告警（不进 `alarm` 列表），只是"定时扫描把每个服药槽只提醒一次"的去重账本。设备本地声光提醒为主、云端 WS 提醒是监护端兜底；去重保证服务重启 / 重扫同一窗口不重复推帧。

```sql
CREATE TABLE plan_reminder (
    id          BIGSERIAL PRIMARY KEY,
    dedup_key   VARCHAR(128) NOT NULL UNIQUE,   -- REMINDER:{planId}:{slotUTC}，唯一约束保证同一槽只推一次
    plan_id     VARCHAR(64),                     -- -> med_plan.plan_id
    elder_id    VARCHAR(64),                     -- -> user.user_id (ELDER)
    slot_utc    TIMESTAMPTZ,                      -- 计划服药槽（UTC 瞬时）
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

**去重口径**：`dedup_key = REMINDER:{planId}:{slotUTC}`（slotUTC 为计划槽的 UTC 瞬时，如 `2026-10-22T16:00:00Z`）；落库时若命中 `dedup_key` 唯一约束冲突 → 跳过（不重复推送）。其余判定与 `med_plan` / `med_record` 的关系见 2.6.1 与下方规则表。

**REMINDER 生成规则（定时扫描）**：

1. **扫描触发**：定时扫描，默认每 60s 一次；窗口 `[now, now + lead-time-minutes]`（默认 10min），只对未来 slot 提醒（已过槽归漏服判定）。
2. **候选计划**：只查 `status='ENABLED' AND sync_state <> 'SYNC_FAILED'`；`sync_state='PENDING'`（未跑同步的测试/演示数据）仍提醒。
3. **槽展开**：按设备时区（`device.timezone`，缺省 `Asia/Shanghai`）在窗口内展开 `times` 候选槽（未来 slot）。
4. **两道拦截**：
   - ① 已服跳过：该槽已有 `med_record`（`plan_time` = slot 瞬时）→ 已吃过不提醒；
   - ② 去重：`plan_reminder` 插入命中 `dedup_key` 唯一约束冲突 → 跳过。
5. **组装与推送**：取该计划全部 `med_plan_item`，逐条组装 `{itemId, medicineId, medicineName, dose, unit}`；推 `REMINDER` 帧到 `elder:{elderId}`。扫描可整体关闭（逃生开关）。
6. **边界**：设备本地为准、云端只兜底——默认不要求设备在线；`times` 非法 → 跳过该槽；无 MAIN 设备用默认时区；单条计划出错不影响其余；WS 未启用/异常静默跳过。

### 2.7 med_record 服药记录（设备上报生成）

```sql
CREATE TABLE med_record (
    id           BIGSERIAL PRIMARY KEY,
    record_id    VARCHAR(64) NOT NULL UNIQUE,   -- 业务ID，如 mr-1001（med_record_biz_id_seq 序列生成）
    elder_id     VARCHAR(64),          -- 冗余：-> user.user_id (ELDER)，便于按老人查询与行级权限
    plan_id      VARCHAR(64),          -- -> med_plan.plan_id
    plan_item_id VARCHAR(64),          -- -> med_plan_item.item_id（定位到具体药品）
    medicine_id  VARCHAR(64),          -- 冗余便于按药品统计（-> medicine.medicine_id）
    capture_id   VARCHAR(64),          -- 关联抓拍留证（-> capture.capture_id，可空）
    actual_dose  VARCHAR(32),
    plan_time    TIMESTAMPTZ,          -- 计划服药时间（按设备时区换算的 UTC）；脏数据/无匹配槽时为 NULL
    actual_time  TIMESTAMPTZ,
    on_time      BOOLEAN,               -- 是否按时（后端重算，非设备上报值）
    source       VARCHAR(16) DEFAULT 'CAMERA',  -- 来源：CAMERA 摄像头识别 / MANUAL 手工补录
    device_id    VARCHAR(64),           -- -> device.device_id
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
```

> **`record_id`**：业务号前缀用 **`mr-`**（如 `mr-1001`）—— 避免与 `guardian_relation.relation_id` 的 `r-` 前缀混淆。取号走独立序列 `med_record_biz_id_seq`（START 1001）。

> **`on_time` 由后端重算（不是设备上报值）**：设备侧算的 `onTime` 仅用于即时声光反馈（03 第 3 章）。入库按「计划时间（`med_plan.times` 就近槽）+ 容忍窗口」重算，容忍时长三级优先级见 §2.6.1。

> **`source` 列**：`up/event/dispense` 的 `source`（CAMERA / MANUAL）落此列；手工补录 / 校准也写 `MANUAL`。**校准与新建时 `source` 恒为 `MANUAL`**，不给设备把已校准记录改回 `CAMERA` 的机会。缺省回退 `CAMERA`。
>
> **补录新建的 `planTime`**：手工补录在"记录不存在=新建"分支，复用就近槽重算 `plan_time`（与 dispense 同口径），使 `miss-alarm` 不会因补录记录的 `plan_time` 为 NULL 被误判漏服；无 `planId` / `times` 为空 / 算不出槽 → `plan_time = NULL`。校准分支（记录已存在）**不改 `plan_time`**（仅覆盖请求体非空字段），避免误触漏服判定。

> **索引**：
> - `uk_med_record_item_plan_time`——`(plan_item_id, plan_time) WHERE 两者非空` 的部分唯一索引，业务幂等第二层（同一计划明细的同一计划时间只写一次；冲突回滚，接受"老人当天同一槽真吃两次被吞"的副作用）；
> - `idx_med_record_elder_time`——`(elder_id, actual_time DESC)`，供记录列表 / 监护端展示；
> - `idx_med_record_plan_time`——`(plan_id, plan_time)`，供 miss-alarm 扫描"某槽有没有记录"。

**med_record 判定规则（服药事件落库）**：

**1 · 消息准入（不通过 → 丢弃，不落库）**

| 序 | 条件 | 结果 |
| --- | --- | --- |
| ① | payload JSON 非法 | 丢弃 |
| ② | `planId` 或 `planItemId` 为空 | 丢弃 |
| ③ | 按 topic 解析的 `deviceId` 查不到 `device`，或 `device.elder_id` 为空 | 丢弃 |
| ④ | `plan` 不存在 | 丢弃 |
| ⑤ | `plan.elder_id` ≠ `device.elder_id` | 丢弃（防跨老人伪造） |
| ⑥ | `planItem` 不存在，或 `planItem.plan_id` ≠ payload 的 `planId` | 丢弃 |

补充：`plan.status = DISABLED` **仍落记录**（服药事实已发生）；`ts` 缺失（null 或 ≤0）时用服务器当前时间；`ts` 为 epoch **毫秒**。

**2 · `plan_time` 就近槽匹配**：取 `ts` 在 `device.timezone`（缺省 `Asia/Shanghai`）下的本地日期 D，生成 **D-1 / D / D+1 三天** × 全部 `times` 的候选槽，取 `|ts − slot|` 最小者为 `plan_time`（差值相同取较早槽）；`times` 为空 → `plan_time = NULL`、`on_time = NULL`。

**3 · 容忍时长 `resolveToleranceMinutes`（三级，§2.6.1）**：计划级 `med_plan.miss_alarm_after_min` > 老人级 `alarm_setting.miss_tolerate_min` > 系统默认 **15** 分钟（非空且 >0 才生效，否则下探；老人级无配置行 → 默认）。

**4 · `on_time`（单侧窗口，提前恒为 true，只判迟到）**：`plan_time` 为 NULL → NULL；`actual_time ≤ plan_time + 容忍` → true；`>` → false。

**5 · 库存扣减**：写记录成功后，**同一事务内**按 `device_id = 上报主控` 且 `medicine_id = 事件上报的药品`扣；数量取 `parse(actualDose)`，失败或非正数 → **1**；`GREATEST(quantity − delta, 0)` 不足扣到 0（**不阻断写记录**），无库存行（影响行数 0）→ 仅告警；幂等命中时随事务回滚不扣。

**6 · 幂等（两层）**：① 上行消息 `msg_id` 全局唯一（网关层已完成去重）——冲突直接丢弃；② `uk_med_record_item_plan_time` 部分唯一索引——冲突捕获后回滚并不写。

**7 · 领域事件**：落库成功后发布服药记录事件，供漏服判定（按 `planId`/`planTime`/`planItemId` 判缺服）消费；**不推 WebSocket、不生成任何告警**（归各自判定逻辑）。事件携带 `recordId/elderId/planId/planItemId/medicineId/planTime/actualTime/onTime/deviceId/captureId`。

### 2.9 alarm 告警

```sql
CREATE TABLE alarm (
    id           BIGSERIAL PRIMARY KEY,
    alarm_id     VARCHAR(64) NOT NULL UNIQUE,
    elder_id     VARCHAR(64),           -- -> user.user_id (ELDER)
    device_id    VARCHAR(64),           -- -> device.device_id
    plan_id      VARCHAR(64),           -- 关联计划（可空，ENV / DEVICE_OFFLINE 等无计划告警为空）
    medicine_id  VARCHAR(64),           -- 关联药品（可空；MISS 必带）
    type         VARCHAR(24) NOT NULL,  -- MISS / ENV / DEVICE_OFFLINE / DEVICE_FAULT
    level        VARCHAR(16),           -- INFO / WARN / CRITICAL
    message      TEXT,
    read_state   BOOLEAN DEFAULT FALSE,
    handle_state VARCHAR(16) DEFAULT 'OPEN',  -- OPEN / HANDLED
    dedup_key    VARCHAR(128),          -- 告警去重键；唯一索引冲突即跳过
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_alarm_elder_read ON alarm (elder_id, read_state, created_at);
-- 部分唯一索引（dedup_key 非空时才约束），避免定时扫描重复落同一条告警
CREATE UNIQUE INDEX uk_alarm_dedup_key ON alarm (dedup_key) WHERE dedup_key IS NOT NULL;
```

> **`alarm_id`**：业务号前缀用 **`a-`**（如 `a-1001`）—— 命名切忌 `alarm_id_seq`（那是 `alarm.id BIGSERIAL` 自动序列，复用会取到自增主键值）。取号走独立序列 `alarm_biz_id_seq`（START 1001）。

> **`dedup_key`**：告警去重键，让"定时扫描重复扫到同一已判定槽"不产生重复告警。取值约定：
> - `MISS` = `MISS:{planId}:{slotUTC}`（slotUTC 为计划槽的 UTC 瞬时，如 `2026-10-22T16:00:00Z`）；
> - 后续 `ENV` / `DEVICE_OFFLINE` / `DEVICE_FAULT` 等复用同一列（各自前缀），统一收敛告警去重逻辑。
> 落库时若命中 `uk_alarm_dedup_key` 唯一索引冲突 → 跳过（不重复落库、不重复推 WS）。

**MISS 判定规则（定时扫描）**：

1. **扫描触发**：定时扫描，默认每 60s 一次，不消费服药记录事件做即时判定（该事件仅预留）；扫描窗口 `[now - lookback(默认 1440min), now - tolerance]`，`tolerance` = 三级容忍（§2.6.1，计划级 > 老人级 > 系统 15min）。
2. **候选计划**：只查 `status = 'ENABLED' AND sync_state <> 'SYNC_FAILED'`；`sync_state = PENDING`（未跑同步的测试/演示数据）**仍判**（否则永远看不到告警）；设备离线时（可配置，默认开启）若 MAIN 主控不在线则跳过，避免"上报不了 = 漏服"误判。
3. **槽展开**：按设备时区（`device.timezone`，缺省 `Asia/Shanghai`）展开全部 `times` 候选槽。
4. **记录比对**：一次拉取该计划在窗口内的全部 `med_record`，按 `plan_time` 的**瞬时**分组，得到每个槽已有的 `plan_item_id` 集合（`source` 为 CAMERA / MANUAL 都算）。
5. **MISS 判定（一个槽一条告警）**：某槽下，**任一 `med_plan_item` 不在集合内即判 MISS**；生成 **1 条**告警，`message` 列出全部缺失药名（格式 `08:00 计划服药未按时服用：缺 阿莫西林、维生素D`），`alarm.medicine_id` 记**第一个**缺失药，`type = MISS`、`level = WARN`、`plan_id` 记计划、`device_id` 记 MAIN 设备；WS 帧 `medicineIds` 带全部缺失药品（见 02 第 8 章 / 04 第 3 章）。全部 item 都有记录 → 不告警。
6. **去重落库**：`dedup_key = MISS:{planId}:{slotUTC}` 落库，命中 `uk_alarm_dedup_key` 冲突 → 跳过（不二次落库、不二次推 WS）。
7. **推送**：落库成功后推 `ALARM` 帧到 `elder:{elderId}`（payload 见 04 第 3 章）；WS 未启用或推送异常 → 静默跳过；单条计划出错不影响其余。
8. **边界**：`times` 非法字符串 → 跳过该槽；无 MAIN 设备当离线处理；扫描可整体关闭（逃生开关）。**本逻辑不提供 REST**（列表/已读/处理与阈值配置归告警核心）。

**ENV 判定规则（事件驱动）**：

0. **触发**：遥测入库后发布遥测记录事件，由环境告警逻辑消费；无定时全表扫。整体可关闭（逃生开关）。
1. **阈值来源（单一来源 = 老人级）**：按 `elder_id` 取 `alarm_setting.env_threshold`（`EnvThreshold`：`tempMin/tempMax/humiMin/humiMax/luxMax`）；判定链：① `alarm_setting` 行不存在 → 不判定；② `env_threshold` 为 `null` → 不判定；③ 某指标上下限为 `null` → 该指标跳过；④ 温/湿为双向（Min/Max）、光照仅上限（`luxMax`）。样本 `elder_id` 为空 → 跳过。
2. **越界判定（指标级，每条样本最多 3 条告警）**：温度 `value < tempMin` → "低于下限"、`value > tempMax` → "超出上限"；湿度同口径；光照 `value > luxMax` → "超出上限"。比较用数值比较，**等于边界不算越界**。样本某值为 `null` → 该指标跳过（温湿/光照分两条入库各自判定）。
3. **告警落库**：每越界指标 1 条 `Alarm` —— `type=ENV`、`level=WARN`、`device_id` = **传感器自身** `deviceId`（与 `env_sample.device_id` 同源）、`plan_id`/`medicine_id` 为 `null`、`message` = "温度 30.5℃ 超出上限 30℃" / "湿度 35% 低于下限 40%" / "光照 800lux 超过上限 600lux"、`read_state=false`、`handle_state=OPEN`。
4. **去重与恢复**：`dedup_key = ENV:{elderId}:{sensorId}:{metric}:{bucket}`，`bucket` 由 `sampleTime` 按去重窗口（默认 30min）截断的起始瞬时；命中 `uk_alarm_dedup_key` → 静默跳过。数值回落即停止告警，**不另发恢复通知**；窗口过后再次越界可再告警。
5. **推送**：落库成功后推 `ALARM` 帧到 `elder:{elderId}`，`medicineIds` 为空 List。WS 未启用或异常 → 静默跳过；单条样本判定失败只记日志不阻断其余上行。
6. **边界**：整体关闭时不跑；温湿/光照分两条样本各自判定；无新迁移（复用 `dedup_key` 与序列）。零新增 REST（查询/已读/处理与阈值配置归告警核心）。

### 2.13 refresh_token 刷新令牌（轮换制）

```sql
-- 业务 user_id 生成器：'u-' || nextval('user_biz_id_seq')
CREATE SEQUENCE user_biz_id_seq START 1001;

CREATE TABLE refresh_token (
    id          BIGSERIAL PRIMARY KEY,
    token_id    VARCHAR(64)  NOT NULL UNIQUE,   -- 与 refresh JWT 的 jti 一致
    user_id     VARCHAR(64)  NOT NULL,          -- -> user.user_id
    token_hash  VARCHAR(128) NOT NULL,          -- refresh token 的 SHA-256，**不存明文**
    status      VARCHAR(16)  NOT NULL,          -- ACTIVE 生效中 / ROTATED 已轮换 / REVOKED 已撤销
    replaced_by VARCHAR(64),                    -- 轮换后接替它的 token_id（REVOKED 时为空）
    expires_at  TIMESTAMPTZ  NOT NULL,          -- 与 JWT 的 exp 一致
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_refresh_token_user ON refresh_token (user_id);
CREATE INDEX idx_refresh_token_expires ON refresh_token (expires_at);
```

**为什么要落库**：文档 02 第 3 章要求"refresh **轮换**：新的 refreshToken 顶替旧的、旧的立即作废"。
纯 JWT 做不到"作废旧令牌"（签名有效期内依然能用），所以服务端必须记住状态 —— 才能支持轮换、登出与重放检测。

- **只存哈希**：`token_hash` 是 token 的 SHA-256，拖库也换不来可用凭据（token 只需要比对、不需要还原，与密码同理，见文档 01 附录）；
- **轮换**：用 refresh token 换新的时，旧行置 `ROTATED` 并由新行回填 `replaced_by`；
- **重放保护**：再次使用已 `ROTATED` / `REVOKED`（或哈希不吻合）的 token，视为令牌可能已泄漏 —— **撤销该用户全部 refresh token** 并返回 40101；
- **账号注销**：注销把该用户全部生效中的行置 **`REVOKED`** —— **这是 `REVOKED` 唯一的主动触发点**（重放保护是被动触发）。注销后旧 access token 最长 2 小时仍可用，靠 refresh 已撤销兜底；**注销后 refresh 直接 40101**；
- **过期**：`expires_at` 到期即不可用（返回 40101），不牵连其它会话；过期记录由清理任务删除。

> `user_biz_id_seq`（START 1001）用于生成 `user.user_id`（如 `u-1001`），用独立序列而非插入后回填，省掉一次 UPDATE。

### 2.14 idempotency_record 幂等记录（`X-Request-Id` 去重）

```sql
CREATE TABLE idempotency_record (
    id                BIGSERIAL PRIMARY KEY,
    request_id        VARCHAR(64) NOT NULL,     -- 客户端 X-Request-Id
    endpoint          VARCHAR(64) NOT NULL,     -- 幂等作用域，当前只有 AUTH_REGISTER
    request_hash      VARCHAR(64) NOT NULL,     -- 请求体指纹（不含密码）
    response_snapshot TEXT        NOT NULL,     -- 首次响应的 data 快照（JSON 字符串）
    expires_at        TIMESTAMPTZ NOT NULL,     -- 过期后不再回放
    created_at        TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (request_id, endpoint)
);
CREATE INDEX idx_idempotency_expires ON idempotency_record (expires_at);
```

- **键**是 `(request_id, endpoint)`：同一个 `X-Request-Id` 在不同接口之间互不干扰；命中即回放首次响应，保证"重复提交只生效一次"；
- **同号不同内容**（换了手机号 / 角色却复用同一个号）按 **40001** 处理 —— 那是客户端用错了号；
- **指纹不含密码**：同号重发视为同一次提交（密码不在指纹里，避免"改个密码重发"被误判）；
- **当前只保护 `POST /auth/register`**（`endpoint=AUTH_REGISTER`）：登录 / 刷新天然幂等，不落记录 —— 免得把含 token 的响应快照写进库里；
- **TTL**：默认 24 小时，过期后不再回放，记录由清理任务删除。

### 2.15 mqtt_message MQTT 上行去重

```sql
CREATE TABLE mqtt_message (
    id          BIGSERIAL PRIMARY KEY,
    msg_id      VARCHAR(96)  NOT NULL UNIQUE,   -- 上行消息 msgId（**全局唯一**：协议保证它已含 deviceId）
    device_id   VARCHAR(64)  NOT NULL,          -- -> device.device_id（解析自 topic 第 3 层）
    topic       VARCHAR(128) NOT NULL,          -- 完整上行 topic，便于排障
    received_at TIMESTAMPTZ  DEFAULT NOW(),     -- 首次处理时间
    expires_at  TIMESTAMPTZ  NOT NULL           -- 过期后可删除（默认 7 天）
);
CREATE INDEX idx_mqtt_message_expires ON mqtt_message (expires_at);
```

- **为什么需要它**：设备断线重连会重发未完成确认的上行消息（见文档 03 第 1 章），不去重就会**重复写服药记录 / 重复生成告警**；
- **键是 `msg_id`**（格式 `{deviceId}-{10位递增序号}`，协议已保证全局唯一），无需按设备再做联合唯一；
- **用法必须是"先 INSERT 抢唯一键"**，命中冲突即判定重复并丢弃 —— **不能"先查再插"**：并发下两条重复消息可以同时通过 SELECT 检查；
- **与 2.14 的 `idempotency_record` 是两回事**（一个管设备上行、一个管 REST 重复提交）：作用域不同、保留时长也不同，**不要合并**；
- **TTL**：默认 7 天，只要覆盖设备的重发窗口；过期记录由清理任务删除。

### 2.16 device_event 设备事件流水

```sql
CREATE TABLE device_event (
    id          BIGSERIAL PRIMARY KEY,
    device_id   VARCHAR(64)  NOT NULL,          -- -> device.device_id（子设备也直接记自己的编号）
    event_type  VARCHAR(24)  NOT NULL,          -- REGISTERED / ONLINE / OFFLINE / FAULT / COMMAND
    detail      VARCHAR(512),                   -- 事件补充描述（如故障原因），可为空
    created_at  TIMESTAMPTZ  DEFAULT NOW()
);
CREATE INDEX idx_device_event_device_time ON device_event (device_id, created_at DESC);

-- device 表补两个索引（服务于高频查询）
CREATE INDEX idx_device_elder  ON device (elder_id);
CREATE INDEX idx_device_parent ON device (parent_device_id);
```

**`event_type` 取值与含义**：

| 取值 | 含义 |
|------|------|
| `REGISTERED` | 设备登记（主控与其子设备各记一条） |
| `ONLINE` / `OFFLINE` | 主控上线 / 离线（MQTT status 与遗嘱驱动） |
| `FAULT` | 设备侧异常（门超时 / 识别失败 / 硬件故障） |
| `COMMAND` | 控制命令下发与回执 |

**约定**：

- **只有状态真的发生跃变才写 `ONLINE` / `OFFLINE`**：主控每 60s 有心跳，若每次上行都写一条，
  一天就是 1440 条噪声，事件流水会被心跳灌满。判跃变靠更新条件带 `online_state != 目标状态`
  （受影响行数 > 0 才算跃变），兼作天然幂等；
- **子设备记自己的 `device_id`**，不折算成主控 —— 详情页按主控查流水时能看到是哪颗传感器出了事，
  而归属老人还是从 `device.elder_id` 取（子设备的 `elder_id` 与父设备一致，见 2.3）；
- **不复用 `mqtt_message`（2.15）**：那张表是上行消息去重账本，只有 `msg_id` 与 topic、
  没有事件类型语义，且 7 天就过期清理。两者作用域与生命周期都不同，**不要合并**；
- **本表无业务号**：事件只在"某台设备的流水"这个作用域内被引用，列表接口返回自增主键即可；
- **`device` 表补索引的原因**：`idx_device_elder` 服务于设备列表的行级过滤（`elder_id IN (...)`），
  `idx_device_parent` 服务于详情查下属子设备（`parent_device_id = ?`）。
  设备表数据量极小（每老人个位数），建索引是为了避免这两条高频查询退化成全表扫描。

### 2.17 device_command 控制命令流水

```sql
CREATE TABLE device_command (
    id           BIGSERIAL PRIMARY KEY,
    command_id   VARCHAR(64)  NOT NULL UNIQUE,    -- 业务ID，如 c-1001（device_command_biz_id_seq）
    device_id    VARCHAR(64)  NOT NULL,           -- -> device.device_id（只接受主控）
    cmd          VARCHAR(24)  NOT NULL,           -- REBOOT / CALIBRATE（BUZZ 蜂鸣 / UNLOCK 解锁由设备本地或小程序本地触发，后端不下发）
    params       JSONB,                           -- 命令参数（可空，如校准参数）
    operator_id  VARCHAR(64)  NOT NULL,           -- -> user.user_id（服务端取鉴权用户，不信客户端）
    state        VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING / SUCCESS / FAILED
    reason       VARCHAR(256),                    -- 失败原因（设备回执 reason / 超时放弃 / 发布失败）
    msg_id       VARCHAR(64),                     -- 下行信封的 msgId（publish 成功后回填），回执按它匹配
    created_at   TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ                      -- 终态时间
);
CREATE SEQUENCE device_command_biz_id_seq START 1001;
CREATE INDEX idx_device_command_device ON device_command (device_id, created_at DESC);
CREATE INDEX idx_device_command_msg    ON device_command (msg_id);
```

**约定（接口见文档 02 的 4.0）**：

- **状态机**：`PENDING`（受理落库并 QoS1 下发）→ `SUCCESS`（设备回执 `up/ack` result=OK）/ `FAILED`
  （回执 FAILED / 5s 超时重发 3 次仍无回执 / MQTT 发布当场抛异常）。终态只翻一次 —— 更新条件带
  `state='PENDING'`，迟到 / 重复的回执天然幂等；
- **回执匹配靠持久化的 `msg_id` 列**（不是内存映射）：服务重启后账本丢失，迟到的回执仍能按
  `idx_device_command_msg` 找到行，只是行多半已是超时 FAILED 终态、幂等不动；
- **`operator_id` 服务端取鉴权用户**：请求体不收 `operator` 字段（客户端多传由 Jackson 忽略），
  留痕以服务端为准；
- **MQTT 未启用不落库**：命令是用户主动的同步操作，悬挂一条永远等不到回执的 PENDING 没意义，
  直接 50000；发布抛异常则落 FAILED 留痕再报 50000；
- **COMMAND 事件契约（`device_event.detail`，前端硬约定）**：JSON
  `{"commandId","cmd","state"[,"reason"]}` —— 下发时写 PENDING 一条、翻终态时再写一条；
  失败原因也进 `reason` 字段。**不生成告警**（02 告警枚举无对应类型，失败在事件流水可见）；
- **不提供命令状态查询 REST / WS 帧**：前端刷 `GET /devices/{id}/events` 观察终态（见 02 的 4.0）。

### 3.1 drug_manual 说明书（监护人上传的原始图片 / PDF）

```sql
CREATE TABLE drug_manual (
    id           BIGSERIAL PRIMARY KEY,
    manual_id    VARCHAR(64) NOT NULL UNIQUE,
```

### 3.2 drug_manual_chunk 说明书分块（RAG 召回单元）

```sql
CREATE TABLE drug_manual_chunk (
    chunk_id     BIGSERIAL PRIMARY KEY,
    manual_id    BIGINT NOT NULL,        -- -> drug_manual.id
    medicine_id  VARCHAR(64) NOT NULL,   -- -> medicine.medicine_id（召回过滤维度）
    elder_id     VARCHAR(64),            -- 召回过滤维度（可空=公共药品）
    page         INT,
    chunk_index  INT,                    -- 块序号，便于答案标注出处
    content      TEXT NOT NULL,          -- 切块后正文（OCR 转写结果）
    source_type  VARCHAR(32) NOT NULL,   -- OCR / MANUAL / PDF
    embedding    vector(1024),           -- 本地 bge-m3 = 1024 维；换模型必须重建向量
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
-- 向量近邻索引（HNSW + 余弦）
CREATE INDEX ON drug_manual_chunk USING hnsw (embedding vector_cosine_ops);
```

### 3.3 召回检索（带过滤，避免跨药品 / 跨老人召回）

```sql
SELECT chunk_id, medicine_id, content,
       embedding <=> :qvec AS distance
FROM drug_manual_chunk
WHERE medicine_id = :mid
ORDER BY distance
LIMIT 5;
```

约束：`embedding` 维度必须与所选 embedding 模型一致 —— **本地 `bge-m3` 为 1024 维**（若改用其他模型，须同步改维度并**重建全部分块向量**，否则检索结果无意义）；`<=>` 为余弦距离算子；召回尽量带 `medicine_id` / `elder_id` 过滤；分块保留页码 / 块序号 / 来源，便于答案标出处。Spring AI `PgVectorStore` 亦可自动建表（`dimensions=1024`、`distance-type=COSINE_DISTANCE`、`index-type=HNSW`），字段名按框架默认即可，与上表等价。
