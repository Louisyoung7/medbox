## 1. 服药记录与依从性

**记录模型**：一条 `med_record` = **某计划的某号格在某次计划时间窗内的一次取药事实**。记录只带 `planId` / `cellNo`（1/2/3）/ `planTime` / `actualTime` / `onTime` / `takenResult` / `source` / `captureId`，**不带药品、剂量**——格内放什么药由监护人布置，后端不记录。

**接口口径**：

- 列表分页响应按通用约定（`page`/`size`/`total`）；详情由后端 join 计划名返回；列表/详情不暴露文件流，只回传 `captureId`（取文件归抓拍接口）；列表项带 `hasCapture`（缩略图占位，仅 `UNTAKEN` 带图记录为 true）。
- `POST /records/{recordId}/confirm` **单接口双语义**：先按 `{recordId}` 查库：① **命中已有记录 → 纠错**：仅覆盖请求体里**非空**的 `actualTime`/`onTime`/`takenResult`（设备误判 `UNTAKEN` 实则已取时，监护人改写为 `TAKEN`，或反之），`source` 恒置 `MANUAL`；② **记录不存在 → 新建（补录）**：此时路径 `{recordId}` 被**忽略**，由服务端生成新 `mr-` 号并在响应返回，请求体须带 `elderId`/`planId`/`cellNo`（缺任一带 40001，计划查不到带 40401），`source=MANUAL`，`planTime` 按该格就近槽重算（无 `planId` / 该格无排程 / 算不出则 NULL）。
- `POST /records/{recordId}/confirm` 仅 `WRITE_RECORD`（GUARDIAN）可调用，老人写 40301、监护 PENDING 40302。
- **与药品档案无联动**：记录只关联计划与格号，**不引用药品档案**，新增 / 纠错不产生药品侧变更（药品档案见 `02c`）。

### 1.0 依从性统计 `/adherence` 与导出 `/records/export`（feat/record-report）

**`GET /adherence?elderId=&period=day|week|month`**（权限 `READ_ADHERENCE`，全角色，老人仅本人）：

- 周期 `period` 为**滚动窗口**：day=最近 24h、week=最近 7 天、month=最近 30 天，终点恒为当前时刻（窗口边界取 UTC 瞬时）；`period` 非法（非 day|week|month，含空）→ 40001。
- 统计口径（**分源**）：
  - `onTimeRate`（按时率）= 周期内 `med_record.on_time=true` 记录数 ÷ 周期内记录总数 `totalDoses`（含 `on_time` 三态，即所有有 `actual_time` 的记录）；
  - `missCount`（漏服数）= 周期内 `alarm.type='MISS'` 条数；**迟到**（`on_time=false` 但有记录）**不计入漏服**，与 07 §2/§5 的 MISS 定义一致；
  - 派生量 `lateCount`（`on_time=false`）、`unjudgedCount`（`on_time=null`，无匹配槽 / 无 `plan_time`）。
- `dailyBreakdown`：按老人 MAIN 设备时区（`DeviceTimezoneResolver`，缺省 `Asia/Shanghai`）做**本地日分桶**趋势（含无数据日，`totalDoses=0` 时 `onTimeRate=0.0`），便于前端画连续折线。
- 响应字段：`elderId` / `period` / `windowStart`(UTC) / `windowEnd`(UTC) / `totalDoses` / `onTimeCount` / `lateCount` / `unjudgedCount` / `onTimeRate`(0.0~1.0) / `missCount` / `dailyBreakdown[]`（`date` yyyy-MM-dd、`onTimeRate`、`totalDoses`、`onTimeCount`、`missCount`）。

**`GET /records/export?elderId=&from=&to=`**（权限 `EXPORT_RECORD`，**监护人可导出、老人不可**；越权 / PENDING → 40301 / 40302）：

- 响应为 **CSV 文件流**（带 UTF-8 BOM 便于 Excel），**不走 `R<T>` 包装**。
- `from`/`to` 可选（ISO-8601）：都不传 → 默认**最近 30 天**（`to=now`、`from=now-30d`）；仅传其一 → 另一边界按 30 天窗口推导；格式非法 → 40001。
- CSV 列（表头 + 数据行，值含逗号/引号时按 RFC 4180 转义）：`记录ID,老人ID,计划名,格口号,计划时间,实际时间,是否按时,结论,来源,抓拍ID,设备ID`。其中时间列 ISO-8601；`是否按时` 取 `on_time` 的 `true/false`（空为 ""）；`结论`=`takenResult`、`来源`=`source`。**不含药品 / 剂量列**。

### 1.1 手动补录与纠错（不再有"待确认"）

设备上报已二值化（`takenResult` = `TAKEN` 已取药 / `UNTAKEN` 未取药，详见 `02b_设备管理.md` §1.1 / `07_业务规则.md` §1）：`UNTAKEN` 记录**为终态、不再要求监护人复核 / 确认**，其抓拍原图仅作留证回看、不强制处理。因此本系统**不再有「待确认」派生态**，列表不再提供 `pendingConfirm` 过滤。

- **手动补录**：当设备未上报（离线 / 老人或他人代服等）时，监护人可经 `POST /records/{recordId}/confirm`（记录不存在 → 新建分支）补录一条 `med_record`（`source=MANUAL`，须指明 `elderId` / `planId` / `cellNo`）。
- **纠错**：当设备误判（如实际已取却报 `UNTAKEN`，或反之）时，监护人可经同一接口（记录存在 → 纠错分支）把 `takenResult` 改写为 `TAKEN`/`UNTAKEN` 纠正；监护人看图留证（`GET /captures/{captureId}/file`）仅为辅助判断、非强制流程。
- **MISS 不受影响**：漏服（`MISS`）仅由"规定时间内该格无上报"触发（见 `07_业务规则.md` §1 / §2），与是否补录无关；超时未补录的缺报**仍判 MISS**。
