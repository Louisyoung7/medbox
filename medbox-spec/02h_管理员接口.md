# 02 · 管理员接口（REST 模块分册）

> 本文件是 `02_REST接口设计.md` 的「管理员接口」分册。通用约定（统一响应 / 错误码 / 权限默认规则）见根文档 `02_REST接口设计.md` §1。

## 1. 管理员接口（测试数据清理，dev/QA 工具）

> 本期 `medbox-admin/` 只做「测试数据清理」这一个 dev/QA 工具（其余管理功能待定，设计见 `09`）。所有接口为 **`ADMIN` 角色门禁**，独立于现有 elder 中心的权限体系（见 01 第 3 章）。
> 角色建模与种子账号见 06 的 2.1（`UserRole` 增加 `ADMIN`）。

基础前缀同现有：`/medbox/api/v1`；所有接口需 `Authorization: Bearer <token>` **且 `role == ADMIN`**，否则 `40301`。

### 1.1 列出用户（供挑测试号）

`GET /api/v1/admin/users`

| Query     | 类型   | 说明 |
|-----------|--------|------|
| `status`  | string | 可选：`ACTIVE` / `DELETED`；缺省=全部 |
| `keyword` | string | 可选：LIKE 匹配 `phone` 或 `username`（仅对非空列生效；软删账号这两列已置 NULL） |
| `role`    | string | 可选：`GUARDIAN` / `ELDER` / `ADMIN` |
| `page`    | int    | 默认 1 |
| `size`    | int    | 默认 20，上限 100 |

- 响应：`R<PageResult<AdminUserRow>>`，`AdminUserRow = { userId, role, name, phone, username, status, createdAt }`。
  - 软删（`status=DELETED`）账号的 `phone` / `username` 已置 NULL，挑选用 `userId` + `status` + `createdAt`。
- 错误：非 ADMIN → `40301`。

### 1.2 清理（硬删 + 级联）

`DELETE /api/v1/admin/users/{userId}`

- 护栏：目标 `status == ACTIVE` → **拒绝**，返回 `40902`（见 1.2）。
- 通过护栏后：**硬删该用户 + 级联清其孤儿数据**（应用层按依赖顺序删，不依赖物理外键）。
- 响应：`R<Void>`（`code=0`）。
- 错误：`40902`（活跃账号）/ `40301`（非 ADMIN）/ `40401`（userId 不存在）。

> **为什么硬删而非软删**：测试痕迹要彻底清除（软删只置 `DELETED` + 清空手机/用户名，但仍留行与孤儿数据，达不到清理目的）；正因如此才要 `ADMIN` + ACTIVE 护栏双重保护。

### 1.3 级联清理范围（按依赖顺序）

目标 `userId` 可能同时是「老人」（拥有 device / medicine / stock / plan / record）与「监护人」（拥有 relation）。**先删子表，再删 `user` 头**，实现前务必对照 06 复核所有 `user_id` / `elder_id` / `guardian_id` 列：

1. `med_plan_item`：`WHERE plan_id IN (SELECT plan_id FROM med_plan WHERE elder_id = ?)`
2. `med_plan`：`WHERE elder_id = ?`
3. `med_record`：`WHERE elder_id = ?`
4. `medicine_stock`：`WHERE elder_id = ?`
5. `device`：`WHERE elder_id = ?`（及其传感器子设备）
6. `guardian_relation`：`WHERE elder_id = ? OR guardian_id = ?`
7. `alarm` / `alarm_setting`：`WHERE elder_id = ?`
8. `capture`：`WHERE elder_id = ?`
9. `user`：最后删除

### 1.4 监控看板聚合查询（feat/backend-admin-dashboard）

> 竞赛演示驱动的**只读聚合**接口，供管理后台看板（`09` 的 `feat/admin-monitor-dashboard`）使用。所有接口落在 `/api/v1/admin/**`，由 `AdminAuthInterceptor` 校验 `ADMIN`（非 ADMIN → `40301`）；本期只读、不改数据、不接生产库强约束。后端实现分支 `feat/backend-admin-dashboard`（见 `07` 第三章）。

基础前缀同 §1：`/medbox/api/v1`；所有接口需 `Authorization: Bearer <token>` **且 `role == ADMIN`**，否则 `40301`；未登录 `40101`。

#### 1.4.1 总览 `GET /api/v1/admin/dashboard/overview`

- 响应：`R<AdminDashboardOverview>`
  - `AdminDashboardOverview = { devices, todayDose, elderCount, planCount }`
  - `devices = { total, online, offline, mqttConnected }`
    - `total / online / offline`：`device` 表按 `online_state` 计数；
    - `mqttConnected`：**`device` 表无独立 `mqtt_connected` 列**，连接态由 `online_state='ONLINE'` 表示，故 `mqttConnected` 取 `online_state='ONLINE'` 计数（与 `online` 同源，看板展示"已联网设备"）。
  - `todayDose = { totalSlots, taken, missed, pending }`：今日（按**各老人设备本地时区**）应服 / 已服 / 漏服 / 待服
    - `totalSlots`：遍历每个有启用计划（`status='ENABLED' AND sync_state <> 'SYNC_FAILED'`）的老人，以其 MAIN 设备 `timezone` 取「本地今日 00:00 ~ 明日 00:00」转 UTC 窗口，用 `PlanSlotResolver` 展开其全部计划 `times` 累加槽数；
    - `taken`：`med_record.on_time=true AND plan_time ∈ 该老人今日窗口`；
    - `missed`：`med_record.on_time=false AND plan_time ∈ 今日窗口`（复用 `miss-alarm` 落库口径，不实时重算）；
    - `pending = totalSlots - taken - missed`。
  - `elderCount`：`"user"` 表 `role='ELDER'` 计数；`planCount`：`med_plan` 表 `status='ENABLED'` 计数。
- 错误：非 ADMIN → `40301`；未登录 → `40101`。

#### 1.4.2 设备网络状态 `GET /api/v1/admin/dashboard/devices`

| Query  | 类型 | 说明 |
|--------|------|------|
| `limit` | int  | 默认 20，上限 50（按 `last_heartbeat` 倒序取最近） |

- 响应：`R<List<AdminDeviceRow>>`
  - `AdminDeviceRow = { deviceId, elderId, elderName, status, lastHeartbeat }`
    - `status`：`online_state` 字符串（`ONLINE` / `OFFLINE`）；`elderName` 由 `device.elder_id` 左联 `"user".name` 取得。
- 错误：非 ADMIN → `40301`。

#### 1.4.3 服药依从率 `GET /api/v1/admin/dashboard/adherence`

| Query        | 类型   | 说明 |
|--------------|--------|------|
| `granularity`| string | 默认 `week`，可选 `week` \| `month`；非法 → `40001` |

- 响应：`R<AdminAdherenceDashboard>`
  - `AdminAdherenceDashboard = { trend, missByHour, byElder }`
  - `trend = [ { bucket, totalSlots, taken, missed, rate } ]`
    - 窗口：`week` → 近 7 天，`month` → 近 30 天（按 UTC 日计）；
    - `totalSlots`：**「当前 `med_plan.times` 按各设备时区展开」近似**（假设窗口内计划稳定；计划曾变动则历史日有偏差，演示可接受）；
    - `taken / missed`：由 `med_record` 按 `plan_time` 的 **UTC 日**分组统计；`rate = taken / totalSlots`；
    - `bucket`：`week` → `yyyy-Www`（ISO 周），`month` → `yyyy-MM`（按日聚合后再归并）。
  - `missByHour = [ { hour, count } ]`：`med_record.on_time=false` 按 `plan_time` 的 **UTC 小时**分桶（演示近似，标注）。
  - `byElder = [ { elderId, elderName, totalSlots, taken, missed, rate } ]`：按老人维度 `rate = taken / totalSlots`，取 top10；`totalSlots` 同上为「当前计划展开」近似，`elderName` 由 `med_record.elder_id` 左联 `"user".name`。
- 错误：非 ADMIN → `40301`；`granularity` 非法 → `40001`。

#### 1.4.4 MQTT 消息流 `GET /api/v1/admin/dashboard/messages`

- 响应：`R<AdminMessageFlow>`
  - `AdminMessageFlow = { upTotal, upLastMinute, downTotal, downLastMinute }`
  - `upTotal / upLastMinute`：来自 `mqtt_message`（见 06 §2.15，**仅上行去重**）；`upLastMinute = received_at >= now - 1min`；
  - `downTotal / downLastMinute`：来自 `device_command`（见 06 §2.17，下行命令）；`downLastMinute = created_at >= now - 1min`。
  - **注**：原草案误将下行写进 `mqtt_message`——`mqtt_message` 只记录上行，`device_command` 才是下行事实来源，本端点下行走 `device_command`。
- 错误：非 ADMIN → `40301`。
