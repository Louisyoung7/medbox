## 1. 服药计划与提醒

药箱固定 **3 个带锁药格**（格号 **1 / 2 / 3**，由固件固定对应早 / 中 / 晚）。服药计划的本质是**"几点开几号格"的排程**：后端只保存并下发 **`时间 → 格号`** 映射，**不保存、不校验、也不下发格内放什么药**。

计划保存后，后端把排程转成设备可执行的定时任务，并通过 MQTT 下行同步给设备；提醒触发以设备本地时钟为准，云端做兜底与统计。

> **一老人一计划、三个固定槽**：每位老人（以其 `MAIN` 药箱为准）**至多一个计划**；计划由 1~3 个 `slots` 组成，每个 `slot = {cellNo, time}`。`cellNo` 只能取 **1 / 2 / 3** 且不重复；**缺失的格号表示该格当天不提醒、不解锁**。计划与药品目录、库存**无任何关联**。
>
> **两处口径**：① `slot.time` 为**设备本地墙钟时间**（`HH:mm`，时区取 `device.timezone`，默认 `Asia/Shanghai`），不是 UTC；② 漏服容忍时长优先级为 **`missAlarmAfterMin`（计划级）> `alarm_setting.missTolerateMin`（老人级）> 系统默认 15 分钟**，计划级留空即沿用上一级。

**接口口径与规则**：

- **slots（时间 → 格号）—— 设备本地墙钟，非 UTC**：数组长度 1~3；`cellNo` ∈ `1/2/3` 且计划内不重复；`time` 格式 `HH:mm`；提交与回显均为原样字符串，**不做任何时区换算**；回显按 `cellNo` 升序。PUT 为**整体覆盖**（`slots` / `repeatRule` / 报警规则全量提交，未提交的格号即视为停用）。
- **一老人一计划**：同一 `elderId` 已存在计划时，`POST /plans` 返回 **40901**；修改沿用 `PUT /plans/{planId}`，不新建第二条。`GET /plans?elderId=` 返回 0 或 1 条。
- **计划与药品、库存无关**：创建 / 修改计划**不再校验库存**，也不会因"药品无库存"被拒绝；药品目录与库存是独立的手工台账（见 `02c`）。
- **启停与 syncState**：`PATCH /plans/{planId}/status` 请求体为 `{status: 'ENABLED'|'DISABLED'}`；`syncState` 仅回显——创建后初始值恒为 **`PENDING`**，真正的 `SYNCED_TO_DEVICE` / `SYNC_FAILED` 由设备同步写入；前端须兼容 `PENDING` 展示为"待同步"，未知值原样展示、无字段不渲染。
- **设备同步映射**：创建 / 修改 / 启用（`ENABLED`）→ 下行 `down/schedule` 的 `op=UPSERT`（载荷含完整 `slots`）；删除 / 停用（`DISABLED`）→ `op=DELETE`；设备回执 `up/ack` 后翻 `SYNCED_TO_DEVICE`，回执 `FAILED` 或超时重发 3 次仍无回执则翻 `SYNC_FAILED`。无老人 MAIN 设备 / MQTT 禁用时安全降级，`syncState` 保持 `PENDING`。
- **权限与老人上下文**：写操作（创建 / 修改 / 启停 / 删除）仅 `WRITE_PLAN`（02_REST接口设计.md §1.3 矩阵，GUARDIAN）；服务端强校验。`elderId`：老人端取自身；监护人端从可见设备归纳。
- **时间线**：`GET /plans/{planId}/next-doses` 按 `slots` 展开未来服药时间线 —— `days` 默认 7、上限 60（越界 40001），本期仅 `DAILY`，停用计划返回空、按 `device.timezone` 换算 `scheduledTimeUtc` / `scheduledTimeLocal`；每条含 `cellNo`，**不含药品信息**。前端**不自行换算时区、不做按次展开**（全在后端完成，前端只消费 `scheduledTimeLocal`）；时间线只读，`READ_PLAN` = 全角色可读，老人端同样可见。
- **本期不做（后端）**：时间线页面前端归后续分支；计划级 `missAlarmAfterMin` / `alarmRule` 编辑（走后端默认与老人级 `alarm_setting`）。
