# 01 · 系统架构与产品定义

> 协议：HTTP REST、MQTT（EMQX）、WebSocket　|　通信：局域网（内网）
> 本文档为 `medbox-spec/` 的**统一约定与全局口径**（时区 / 权限 / 鉴权 / 过期等以本文件为准）；数据库设计见 `06`，判定 / 生成类业务规则见 `07`，接口契约见 `02` 及其分册，设备接入见 `03`，实时推送见 `04`，AI 洞察见 `05`。

## 1. 项目背景与产品定位

面向**居家养老场景**的家用智能药品箱管理系统：设备端以**药箱主控（单片机 / 嵌入式网关）**为核心，负责定时提醒、人机交互与无线通信，并通过 WiFi 挂接**温湿度、光照等传感器子设备**；**摄像头独立经 HTTP 直连后端上报服药事件**（端侧判定格子是否被取走得出取药结论 + 仅未取药时附抓拍原图，见第 4 章 / `02b_设备管理.md` §1.1；单片机与摄像头内部如何协同是设备实现细节、前后端不约束）；云端由 Java 后端（Spring Boot）承载业务；用户侧为 uni-app 小程序，分老人本人端与监护人的远程监护端；平台管理员不在小程序角色体系内，使用独立 Web 后台。

**适用人群与定位**：

- **面向长期服药人群**：需长期规律用药的慢性病 / 固定用药场景；普通感冒等短期、偶发用药不需要药箱。
- **服药种类相对稳定**：服药计划建立后不会有重大更改，以"长期固定"为主、偶尔微调，而非频繁变动。
- **目标用户**：需要规律服药的老人，或其他有长期用药管理需求的特殊群体；监护侧（家属 / 护理）主要关注"是否按时取药"。

## 2. 药箱物理形态与工作原理

### 2.1 分层物理结构

药箱为**分层结构**：一个 **药箱主控（`MAIN`）** + **上层 3 个带锁药格（每日用药区）** + **下层仓储区**（物理存药空间，系统不建模）。

- **上层**：固定 **3 个带锁药格**，格号 **1 / 2 / 3 由固件固定对应早 / 中 / 晚三次服药**。每格当天放哪几种药由监护人自行布置，**后端不关心格内放什么药**；到点仅解锁"该次对应格"（带锁天然防错拿）。
- **下层**：物理上长期存放药品；系统**不建模库存**（无数量、无日期记录），药品档案（见 §3.2-2）只是与设备解耦的纯手工记录。

### 2.2 每日流程

监护人把当天各次药放入 1/2/3 号格 → 到点**单片机本地声光 + 解锁对应格** → 老人取药 → **设备端侧判定该格是否被取走** → **经 HTTP 上报取药结论（`TAKEN`/`UNTAKEN`，带格号）；仅 `UNTAKEN` 附抓拍原图作留证** → 后端**按格号与计划时间落记录；规定时间内无上报 = 该格漏服（`MISS`）**（后端不运行图像识别）。

### 2.3 职责边界（后端只排程与统计）

- **后端只建模"格号 + 时间"**：格位固定为 **1 / 2 / 3（对应早 / 中 / 晚）**，后端数据库只保存每个格位的**计划开格时间**，不保存格内药品、不保存药品与格位的对应关系。除"计划配置"外，后端不下发任何实时提醒 / 声光 / 开格指令。
- **下发方式 = 首次全量 + 变更增量（下发的是配置，不是指令）**：因服药计划"相对稳定"，仅首次把全量计划（**几点开几号格**）下发给主控，之后计划增删改才下发增量更新。下发完成后，单片机**完全本地**按自身时钟判断时间、触发对应格子的声光与解锁。
- **单片机本地闭环**：到点**本地声光 + 解锁对应格**提醒、是否按时取药，全部在单片机本地完成（**提醒形式后端不关心**）；**服药计划下发给主控、主控本地按自身时钟触发格子，与摄像头的内部协同是设备实现细节，前后端不约束**。老人开格取药 → **设备端侧判定格子是否被取走后，直接经 HTTP 上报取药结论（`TAKEN`/`UNTAKEN` + 格号）；仅 `UNTAKEN` 附抓拍原图作留证**；**后端据"结论字段"判已取药 / 未取药，不运行图像识别、不报置信度**；**设备超时未上报 = 漏服（`MISS`）**。单片机同时经 MQTT 上报环境遥测。
- **上报策略（轻量且不丢统计）**：**设备经 HTTP 上报所有服药事件**（取药结论 + 仅未取药时附抓拍原图，无需单片机中转）；正常 `TAKEN` 不上图（轻量）；环境遥测（温湿 / 光照）仍由单片机经 MQTT 上报入库；只有**异常事件**（漏服 / 格子异常 / 环境越界）才额外触发"后端 → 监护端"告警。设备端**离线缓存、联网补传**，避免断网丢记录（环境遥测同理）。
- **后端只剩三件事**：① 下发"时间 → 格号"排程（首次 + 变更）；② 接收服药事件 / 环境遥测；③ 统计（有事件 = 服、超时无事件 = 漏）、展示与人工维护药品档案、同步监护端（依从性看板、告警推送）。
- **职责边界一句话**：后端下发"时间 → 格号"排程、接收事件、做统计与同步；单片机本地调度声光与解锁、本地判定、上报事件（异常触发告警）。

### 2.4 形态要点（保留 / 删除一览）

- **明确保留**：仓储环境监控（温湿 / 光照，保护下层存储药）、药品档案（纯手工记录）；传感器（温湿 / 光照 / 摄像头）全部保留。
- **删除错服监测**：非计划对应格子带锁打不开，错服因带锁天然杜绝，无需监测（原图 + 结论即判定"药是否被取走"，不比对药品）。
- **删除临期 / 过期预警功能**：不再自动判定 / 预警过期；药品档案也**不记录生产 / 有效期等日期字段**。
- **删除库存台账**：药品档案与下位机不互通，记录数量 / 日期没有业务闭环价值；系统不建模库存（无 `medicine_stock` 表、无库存接口），药品档案仅记录"有哪些药"及其文字信息。
- **物理模型反转**：把"格子"从"不划分"反转为"固定 3 格带锁核心物理模型"（上层 3 个带锁药格对应早 / 中 / 晚 + 下层仓储区）。

## 3. 功能范围

### 3.1 核心功能（高层）

覆盖 6 项核心功能：

- 按时提醒服药；
- 按固定 1 / 2 / 3 号药格定时解锁，带锁天然防错拿；
- 监测是否按时取药，规定时间内该格无上报判漏服（`MISS`）；
- 信息互通（本地端与远程监护端数据 / 告警同步）；
- 存储环境监测（温度、湿度、光照）；
- 接入 AI 大模型，对服药记录 / 环境等结构化数据做用药洞察（分析 / 预测 / 建议，详见 `05`）。

### 3.2 功能点最终结构（4 业务 + 1 底座）

系统由 **4 个业务功能 + 1 个底座能力** 构成（信息互通作为各功能的"同步监护端"隐性底座，不再单列；技术载体沿用 `04` WebSocket + `03` MQTT）：

1. **服药提醒与按时监测闭环**
   - **输入**：服药计划（`med_plan` 的 `slots`：**格号 → 开格时间**，如 `1 号格 08:00 / 2 号格 12:30 / 3 号格 18:00`；不描述格内药品）。
   - **提醒（已决）**：到点由**单片机本地声光 + 解锁对应格**完成；**后端只下发"时间 → 格号"排程、不实时驱动、不关心提醒形式**（见 §2.3）。
   - **识别与判定（已决）**：**设备端侧判定该格是否被取走，直接经 HTTP 上报取药结论（`TAKEN`/`UNTAKEN`）+ 格号；仅 `UNTAKEN` 附抓拍原图作留证**；**后端不运行图像识别、不报置信度**，据**结论字段**入库统计（已取药 / 未取药）；**设备超时未上报**仍作为最终兜底判漏服（`MISS`）。
   - **统计与同步**：`UNTAKEN` 记录为终态、**不再要求监护人复核**（监护人可在设备未上报时手动补录 / 纠错，见 `02e` §1.1）；未按时且**设备超时未上报**生成 `MISS` 告警并同步监护端，**告警只提格号与时间、不提药品名**；漏服容忍时长优先级沿用现有设计。
   - **错服天然杜绝**：非计划对应格子带锁打不开，无需监测错服（见 §2.4）。
2. **药品档案（纯手工记录）**
   - **定位（已决）**：药品档案与下位机不互通，本质是**纯记录**——只记录"有哪些药"及其文字信息（名称 / 规格 / 参考单次用量 / 单位 / 禁忌 / 储存条件），供监护人 / 医生查看。
   - **不记录库存**：无数量、无生产 / 有效期日期，**无库存表与库存接口**；服药事件、补录、纠错均不产生任何库存联动。
   - **与格位无关**：药品档案与设备、格位**没有绑定关系**，后端不记录、不校验。
3. **服药记录与依从统计**
   - 历史服药记录查询（按时 / 漏服，记录来源 = 设备端侧判定并上报的该格取药结论）；按时率、漏服次数等**依从性统计看板**，供监护人掌握老人用药规律。
4. **已服手动补录 / 纠错**
   - 设备未上报（离线 / 代服等）时，提供**手动补录服药记录**的兜底入口；设备误判（如 `UNTAKEN` 实则已取）时提供**纠错**入口，避免漏记、补全记录。**本期不再有"待确认 / 复核"强制流程**。
5. **底座 · 信息互通（隐性）**
   - 本地端与远程监护端的数据 / 告警同步，技术载体为 `04` WebSocket + `03` MQTT，贯穿上述各功能，不再单列。

### 3.3 已评审决策补充说明

- **一个监护人可绑定多个老人**：由现有 `guardian_relation`（多对多）天然支持，非新增功能点。
- **异常实时推送**：当前沿用 WS / 小程序推送；**短信 / 微信消息作为后续增强**，本期不做。
- **未纳入本期**：远程看护（实时画面）、异常行为监测、紧急求助、AI 用药教育推送——列为后续评估，避免回到过度复杂。
- **接入 AI 大模型（洞察层）**：对本项目已有的结构化数据（服药记录 / 计划 / 环境等）做**分析、预测、提建议**（用药依从性归因、计划时序建议、环境-用药关联、周期趋势预警）。由监护人**自带 API Key（BYOK）**，后端不托管大模型、不为多用户承担 LLM 高并发；若 `baseUrl` 指向局域网内自建端点（如本机 Ollama），则连出网都不需要。**不再做本地 OCR / Embedding 与说明书 RAG**。设计见 `05`。

## 4. 系统架构与协议分工

| 协议 | 链路 | 承载内容 |
|------|------|----------|
| HTTP / REST | 小程序 ⇄ 后端 | 登录鉴权、账号 / 设备 / 药品 / 计划增删改查、历史与统计查询、AI 洞察 |
| MQTT（EMQX） | 设备 ⇄ 后端 | 设备遥测上报、环境 / 异常事件上报、云端下行（仅下发计划配置与运维命令 REBOOT / CALIBRATE）。**服药事件不再走 MQTT**：设备经 HTTP 直连后端上报取药结论（`TAKEN`/`UNTAKEN`）+ 仅未取药时附原图（见第 4 章 / `02b_设备管理.md` §1.1），本通道不再承载 |
| HTTP（服药上报 / 图片上传） | 摄像头 → 后端 | 设备端侧判定格子是否被取走后**直连后端** multipart 上报取药结论（`TAKEN`/`UNTAKEN`）；**仅 `UNTAKEN` 附抓拍原图**作留证，正常 `TAKEN` 不上图，不过 MQTT、不过单片机（见 §2.2 / `02b_设备管理.md` §1.1） |
| WebSocket | 后端 → 小程序 | 告警实时推送、设备在线状态、实时监测看板 |

MQTT 消息中间件统一使用 **EMQX**（局域网内网部署，详见第 6 章与文档 `03`）。

## 5. 角色与权限模型

采用 RBAC + 数据归属双重控制。小程序侧角色与默认权限（接口级细则见 `02_REST接口设计.md` §1.3）：

| 角色 | 说明 | 默认权限（关键权限） |
|------|------|----------|
| 老人本人（`ELDER`，用药人） | 设备近场使用者 | 只读本人数据（计划 / 记录 / 告警 / 设备状态）、AI 洞察、本地查看 |
| 监护人（`GUARDIAN`，统一单一角色） | 远程监护端（涵盖子女 / 护理 / 医生，不再细分） | 对已生效监护关系下的老人可读可写（计划、药品档案、告警处理、阈值、AI Key）、处理 / 确认告警、导出记录、制定 / 修改服药计划、查看依从性报告（导出记录覆盖全部监护人，见 `Permission` 矩阵 `EXPORT_RECORD`） |
| 设备端 | 药箱主控 / 传感器（温湿度 / 光照） | 走 **MQTT**（上报遥测 / 事件、接收下行命令）；**摄像头独立走 HTTP** 直连后端上报服药事件（取药结论 + 仅未取药时附原图），不参与小程序角色体系 |
| 平台管理员（`ADMIN`） | 设备准入审核、字典与阈值模板维护等运营职责 | **不在小程序角色体系内**，由 Web 管理后台承载（见下） |

**权限原则**：所有查询 / 操作以"当前登录用户对目标老人 / 设备是否具有监护或管理关系"为校验依据，越权返回 40301。

监护关系为**两步生效**：监护人发起申请（PENDING）→ 老人端确认（ACTIVE）；未确认前访问该老人数据返回 40302。校验顺序：登录 → 监护关系 → 关系是否生效 → 该角色是否具备此操作权限。

**平台管理员**：设备准入审核、字典与阈值模板维护等运营职责**不在小程序角色体系内**，由后续设计的 **Web 管理后台** 承载，拥有独立账号体系与鉴权方式（本期只做「测试数据清理」dev/QA 工具、分支 `feat/admin-testdata-cleanup`，设计见归档 `archive/09`；管理员接口契约见 `02` 第 10 章）。本文档集所列 REST / MQTT / WS 接口仅面向小程序端与设备端，管理员相关接口不在范围内。凡涉及管理员的操作（如设备准入审核）在 Web 后台完成，小程序端至多发起申请或查看状态。

## 6. 局域网（内网）部署与地址规划

当前阶段系统全部通信均在同一局域网（同一子网）内完成，暂无公网域名与公网 IP：设备、Java 后端、EMQX 与 uni-app 小程序均部署 / 接入同一内网。所有接口路径不变，仅将"域名"替换为"内网 IP + 端口"。

后端、小程序与 Web 前端同在单仓 `medbox`，按目录区分（目录结构详见 `00` 索引与根 `README.md`）。

### 6.1 服务地址与端口规划

各服务地址集中在后端配置（`application.yml`）与小程序端统一配置（`BASE_URL` / `WS_URL`）中，换 IP 时一处修改、全局生效；入库配置不含任何 IP，本机差异经不入库的本地文件覆盖。下表 IP 以 192.168.1.10 为例：

| 服务 | 协议 / 端口 | 内网地址示例 | 备注 |
|------|-------------|--------------|------|
| Java 后端 (REST) | HTTP / 8080 | `http://192.168.1.10:8080/medbox/api/v1` | 默认明文 |
| WebSocket 推送 | WS / 8080（同后端不同路径） | `ws://192.168.1.10:8080/medbox/ws` | 亦可独立端口 8081 |
| MQTT Broker（EMQX） | TCP / 1883 | `tcp://192.168.1.10:1883` | **仅设备端与后端使用**；EMQX Dashboard：`http://192.168.1.10:18083` |
| Web 前端 `medbox-admin`（Vite dev） | HTTP / 5173 | `http://192.168.1.10:5173` | ⏸ **本期仅 `feat/admin-testdata-cleanup`**（测试数据清理工具，设计见归档 `archive/09`）；其余管理功能待定；需后端放行 CORS 或用 dev proxy |

> **小程序不直连 MQTT**：按第 4 章的协议分工，MQTT 只用于"设备 ⇄ 后端"，小程序侧**只有 `BASE_URL` 与 `WS_URL` 两个地址**，不需要也不配置 `MQTT_URL`。设备上报由后端消费后经 WebSocket 推给小程序；小程序下发的计划 / 命令走 HTTP，由后端转 MQTT 下行。EMQX 无需开启 WebSocket 监听器。

> **出网范围**：仅公网大模型 Chat 调用出网（放行监护人所选模型的域名 / IP，见 `llm_config.baseUrl`）；**后端不托管大模型、不本地化 OCR / Embedding**（采用 BYOK，详见文档 `05` 第 0.4 章）。若 `baseUrl` 指向局域网内自建端点，则连出网都不需要。

各子项目的本地配置细节（后端 `application.yml` / `application-local.yml`、PostgreSQL 17 + Flyway 建表、uni-app 的 `BASE_URL` / `WS_URL` / `.env.local`、Web 前端的 dev proxy 等）见各自 `README.md`：`medbox-server/README.md`（「准备数据库」「连接配置」「建表（Flyway）」「MQTT」）、`medbox-miniapp/README.md`（「后端地址配置」）、`medbox-admin/README.md`（「后端地址配置」）。

## 7. 关键业务流程串联

### 7.1 按时服药与漏服告警

后端将 MedPlan（`slots`：格号 → 开格时间）经 MQTT down/schedule 同步到设备 → 设备（单片机）到点**本地声光 + 解锁对应格**提醒并等待取药 → **设备端侧判定该格是否被取走后直接经 HTTP 上报取药结论（`TAKEN`/`UNTAKEN`）+ 格号；仅 `UNTAKEN` 附抓拍原图**（见 `02b_设备管理.md` §1.1 / `03` 第 4 章；单片机与摄像头内部协同不约束前后端）→ 后端按**格号 + 就近时间槽**判已取药 / 未取药、落一条 MedRecord。若容忍时长内**该格无上报**，后端定时任务按槽判定生成 MISS 告警（message 只提"几点、几号格未取药"，不提药品名），落 Alarm 并经 WebSocket 推送监护端。

### 7.2 服药识别（端侧药格占用检测：是否取药）

**是否拿对药由带锁药格天然杜绝**（非计划对应格打不开），无需识别药品；是否**已取药**改由**设备端侧判定该格是否被取走**完成，并**直接经 HTTP 上报取药结论（`TAKEN`/`UNTAKEN`）+ 格号；仅 `UNTAKEN` 附抓拍原图作留证**（摄像头支持 HTTP；单片机与摄像头内部如何协同是设备实现细节、前后端不约束，见 `03` 第 4 章）。后端**不运行图像识别、不报置信度**；`UNTAKEN` 原图留存后端作留证回看，**不再要求监护人复核**（见 `02b_设备管理.md` §1.1 / `02e` §1.1）。

### 7.3 环境超标

**传感器是药箱下的子设备**（温湿度 / 光照等各自有 `device_id`），数据由主控（唯一 MQTT 连接）统一转发，消息中带 `sensorId` 标明来源；**子设备没有 MQTT 连接与遗嘱**，其在线状态由主控通过 `up/sensor/heartbeat` 周期汇总上报 → 后端按**该老人 `alarm_setting.env_threshold`**（温湿光上下限，老人级统一配置，不按药品细分）判定 → 越界生成 ENV 告警并推送；小程序经环境监测接口按传感器拉取曲线展示。

### 7.4 AI 洞察层（分析 / 预测 / 建议）

监护人 / 小程序调用 `POST /ai/insight`（或流式 `POST /ai/insight/stream`）：后端校验权限，按 `elderId` 取出监护人配置好的大模型 Key（BYOK），拼装该老人的结构化数据（服药记录 / 计划 / 环境等）为上下文，调用大模型生成自然语言洞察（含 `disclaimer`，不落库、不自动执行）；系统亦可定时批量生成并经 WebSocket 推送（详见文档 `05` 第 2 章）。
