## 0. 背景与变更性质

- **原规划（当前 `02`~`09` 版本）的核心假设**：
  - 药箱 = **智能仓储**：自动库存扣减（`medicine_stock`）、环境监测（`env_sample` + ENV 告警）、临期/过期预警（`EXPIRED`）。
  - 药箱**不划分格子/仓位**，药品按"药箱 + 药品"维度管理（见 `06` 2.3 / 2.5 / 2.6 注释）。
- **新形态（根本性调整）**：
  - 药箱 = **分层结构**：**上层 = 每日用药区（带锁分格）**，每个格子放"当天某次要吃的药"，到点只解锁计划对应格；**下层 = 仓储区**，长期存放药品库存。库存数量与每次服药的**应消耗量**由**监护人手动录入/调整**（药箱不自动识别）；后端据摄像头上报的**已服事件**判断本次是否实际服药，命中则按监护人录入的应消耗量**计算并扣除**当前库存、展示并提供人工修改入口（扣减由后端执行，漏服不扣）。
  - 数据流：提醒由**单片机本地声光**完成（后端不关心提醒形式）；取药识别在**摄像头端侧人脸识别**完成——摄像头识别到本人服药后**直接经 HTTP 把抓拍原图 + 自报置信度 + 是否服药结论字段上报后端**（摄像头支持 HTTP，与单片机内部如何协同是设备实现细节，前后端不约束）；**后端不运行图像识别**，但接收并使用摄像头自报的置信度（低于阈值即标记待确认，供人工复核），据结论字段入库统计（已服/未服/待确认）；**摄像头超时未上报图片即判漏服（`MISS`）**。错服因带锁天然杜绝（非计划格打不开）。
- **变更性质**：相对原规划，保留仓储（自动扣减降级为监护人手动录入 + 后端据已服事件扣减）、**保留环境监测**（仓储需要温湿/光照保护）；删除错服监测（带锁）、**删除临期/过期预警功能**；把"格子"从"不划分"反转为"带锁核心物理模型"。属于物理模型反转 + 能力升降调整。

## 1. 新形态的产品定义

### 产品定位与适用人群

- **面向长期服药人群**：针对需长期规律用药的慢性病 / 固定用药场景；普通感冒等短期、偶发用药不需要药箱。
- **服药种类相对稳定**：服药计划建立后不会有重大更改，以"长期固定"为主、偶尔微调，而非频繁变动。
- **目标用户**：需要规律服药的老人，或其他有长期用药管理需求的特殊群体；监护侧（家属 / 护理）主要关注"是否按时取药"，以及库存 / 临期是否需补药。

### 1.1 药箱基本形态（物理）

- **分层物理结构**：一个 **药箱主控（`MAIN`）** + **上层带锁分格（每日用药区）** + **下层仓储区（库存）**。
  - **上层**：每个带锁格子放"当天某次要吃的药"，**仅"计划对应格子"在到点时可解锁**（带锁天然防错拿）。
  - **下层**：长期存放药品库存；**初始库存数量**与**每次服药应消耗量**由监护人**手动录入**；后端据摄像头上报的**已服事件**判定是否本次服药，命中则按监护人录入的应消耗量**计算并扣除**当前库存、展示并支持人工修改（漏服不扣）。
- **每日流程**：监护人布置上层格子（每日药，手动录入消耗）→ 到点单片机**本地声光 + 解锁对应格** → 老人取药 → 摄像头**端侧人脸识别** → **经 HTTP 上报抓拍原图 + 自报置信度 + 是否服药结论字段** → 后端**据结论字段 = 已服、超时无图片 = 漏服（MISS）**，置信度低于阈值标记待确认（后端不运行图像识别）。
- **明确保留**：仓储环境监控（温湿 / 光照，保护下层存储药）、库存管理（手动录入驱动）。传感器（温湿 / 光照 / 摄像头）全部保留。**删除药物过期/临期预警功能**（不再自动判定/预警过期；`production_date`/`expiry_date` 仍可作为记录字段，但系统不据其告警）。

### 1.2 角色（简化）

- 老人（`ELDER`，用药人）、监护人（`GUARDIAN`，**统一单一角色**）、管理员（`ADMIN`，仅测试数据清理）。
- **简化决策**：监护人不区分"家属/医生/护理"形态，统一为单一 `GUARDIAN` 角色，避免权限矩阵过度复杂。绑定流程（申请 → 老人确认 → `ACTIVE`）与权限边界（`ACTIVE` 期间可读写老人数据）沿用，仅去掉角色细分。

### 1.3 通讯与部署（保留）

- 局域网为主，沿用 **MQTT(EMQX) 上行 + WebSocket 推送 + HTTP REST 读写**。设备注册/心跳/命令/去重等基础设施不变。

### 1.4 设备职责与计划下发模式（架构决策 · 后端极简）

- **后端不建模格子、不下发实时指令**：格子是药箱本地的物理概念，后端数据库不出现 `cell_id`；除"计划配置"外，后端不下发任何实时提醒/声光/开格指令。
- **下发方式 = 首次全量 + 变更增量（下发的是配置，不是指令）**：因服药计划"相对稳定"（见产品定位），仅首次把全量计划（时间 + 药品明细）下发给主控，之后计划增删改才下发增量更新。下发完成后，单片机**完全本地**按自身时钟判断时间、触发对应格子声光、计算闪/响哪些格子。
- **单片机本地闭环**：到点**本地声光 + 解锁上层对应格**提醒、是否按时取药，全部在单片机本地完成（**提醒形式后端不关心**）；**服药计划下发给主控、主控本地按自身时钟触发格子，与摄像头的内部协同（谁触发抓拍、如何取流）是设备实现细节，前后端不约束**。老人开格取药 → **摄像头端侧人脸识别后直接经 HTTP 把抓拍原图 + 自报置信度 + 是否服药结论字段上报后端**（摄像头支持 HTTP）；**后端据"结论字段"判已服/未服/待确认、据摄像头自报置信度是否低于阈值标记待确认，原图与置信度均为上报数据、后端不运行图像识别**；**摄像头超时未上报图片 = 漏服（`MISS`）**。单片机同时经 MQTT 上报环境遥测。
- **上报策略（轻量且不丢统计）**：**摄像头经 HTTP 上报所有服药事件**（抓拍原图 + 自报置信度 + 是否服药结论字段，无需单片机中转）；环境遥测（温湿 / 光照）仍由单片机经 MQTT 上报入库；只有**异常事件**（漏服 / 格子异常 / 环境越界）才额外触发"后端 → 监护端"告警。摄像头端**离线缓存、联网补传**，避免断网丢记录（环境遥测同理）。
- **后端只剩三件事**：① 下发计划配置（首次 + 变更）；② 接收服药事件 / 环境遥测；③ 统计（有事件=服、超时无事件=漏）、展示与人工修改库存、同步监护端（依从性看板、告警推送）。
- **职责边界一句话**：后端下发"计划配置"、接收事件、做统计与同步；单片机本地调度声光、本地判定、上报事件（异常触发告警）。

## 2. 功能点（最终结构）

系统由 **4 个业务功能 + 1 个底座能力** 构成（信息互通作为各功能的"同步监护端"隐性底座，不再单列；技术载体沿用 `04` WebSocket + `03` MQTT）：

### 2.1 服药提醒与按时监测闭环

- **输入**：服药计划（`med_plan` 时间槽 + `med_plan_item` 药品明细，仅描述"时间 + 药品"，后端不建模格子）。
- **提醒（已决）**：到点由**单片机本地声光 + 解锁上层对应格**完成；**后端只下发计划配置、不实时驱动、不关心提醒形式**（见 §1.4）。
- **识别与判定（已决）**：**摄像头端侧人脸识别，直接经 HTTP 上报抓拍原图 + 自报置信度 + 是否服药结论字段**（摄像头支持 HTTP，与单片机内部如何协同不约束前后端）；**后端不运行图像识别**，但接收并使用摄像头自报的置信度（低于阈值即标记待确认，供人工复核），据**结论字段**入库统计（已服 / 未服 / 待确认）；**摄像头超时未上报图片**仍作为最终兜底判漏服（`MISS`）。
- **统计与同步**：后端据结论字段入库统计（已服 / 未服 / 待确认）；"待确认"走 `02` 的 §7 待确认与人工确认闭环（监护人看图后调 `POST /records/{recordId}/confirm` 改写 `face_result`）；未按时且**摄像头超时未上报图片**生成 `MISS` 告警并同步监护端；漏服容忍时长优先级沿用现有设计；**"已服"事件同时触发库存扣减（按监护人录入的应消耗量，见 §2.2），漏服不扣**。
- **错服天然杜绝**：非计划对应格子带锁打不开，无需监测错服（见 §0）。

### 2.2 库存与补药提醒（分层仓储 + 手动录入）

- **物理**：药箱**下层为仓储区**长期存药；**上层每日用药带锁分格**仅放当天药（见 §1.1）。
- **手动录入（已决）**：**初始库存数量**与**每次服药应消耗的药品量**，均由监护人**手动录入**；后端据摄像头上报的**已服事件**判断本次是否实际服药，命中则按监护人录入的应消耗量**计算并扣除**当前库存、提供**展示与人工修改入口**（库存非药箱自动识别；扣减由后端执行，漏服不扣）。
- **补药提醒**：当某药库存低于阈值时，提醒监护人**补药 / 更新库存**，避免无药可吃。
- 这是"手动仓储"的必需配套：扣减量由监护人录入、扣减动作由后端执行、是否扣减由摄像头已服事件判定（漏服不扣）——替代原"设备自动识别扣减"，库存维护责任交回监护人。

### 2.3 服药记录与依从统计

- 历史服药记录查询（按时 / 漏服，记录来源 = 摄像头端侧识别上报的服药事件）；按时率、漏服次数等**依从性统计看板**，供监护人掌握老人用药规律。

### 2.4 已服手动确认 / 纠错

- 摄像头端侧判定为"**待确认**"（模糊 / 不确定），或老人 / 他人代服时，提供**人工确认已服、补录或纠正**的兜底入口，避免误告警、补全记录。

### 2.5 接入 AI 大模型（洞察层）

- 大模型接入定位为「洞察层」：对本项目已有的结构化数据（服药记录 / 库存 / 计划 / 环境等）做**分析、预测、提建议**（用药依从性归因、库存耗尽预测、计划时序建议、环境-用药关联、周期趋势预警），由监护人**自带 API Key（BYOK）**，后端不托管大模型、不为多用户承担 LLM 高并发；若 `baseUrl` 指向局域网内自建端点（如本机 Ollama），则连出网都不需要。**不再做本地 OCR / Embedding 与说明书 RAG**。
- 设计见 `05`（方向、功能点、接口）。

**已评审决策（补充说明）**：
- **一个监护人可绑定多个老人**：由现有 `guardian_relation`（多对多）天然支持，非新增功能点。
- **异常实时推送**：当前沿用 WS / 小程序推送；**短信 / 微信消息作为后续增强**，本期不做。
- **未纳入本期**：远程看护（实时画面）、异常行为监测、紧急求助、AI 用药教育推送——列为后续评估，避免回到过度复杂。
