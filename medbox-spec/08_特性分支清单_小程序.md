# 08 · 特性分支清单（uni-app 小程序）

> 每个 `- [ ]` 待办 **对应一个特性分支**，分支名见每条的 `feat/xxx`。
> **修 Bug、重构项目结构不计入本清单**。
> 图例：🧱 = **地基**；🔧 = **功能任务**；🧭 = **判定型**（含业务规则与优先级，**动手前先出规则表给用户确认**，见 `AGENTS.md` 的 3.1）。
> **认领与引用一律用分支名**（如"对应 08 的 `feat/mp-plan`"），**不要用"第 N 项"** —— 清单会重排，序号不稳定。
> 老人端与监护端（子女 / 护理 / 医生）的视图差异，在各功能分支内按 02_REST接口设计.md §1.3 权限规则处理，不单开分支。
> 完成后勾选 `- [x]`，PR 描述写明"对应 08 的 `feat/xxx`"。

> **清单即实施顺序**：第一章地基 → 第二章 **P0 主干闭环** → 第三章 **P1 完善** → 第四章 **P2 改造 + 原 P1 剩余（随文档大改动跟进）** → 第五章 **P3 锦上添花（原 P2，可砍）**。
> P3 整体后置，时间不够可整块砍，不影响主干演示。
> 已按此原则**合并同类分支**：原 38 个待办合并为 **23 个分支**（见各条括号内的"原待办"）。
>
> **本端受后端接口约束**：后端 P0 未落地的接口，对应页面无法联调。因此顺序基本跟随 `07`，只有 `mp-ui-kit`（纯 UI，不依赖后端）可以提前做。
>
> **依赖列统一写成两段**：`本端 xxx`（本端内的前后置分支）+ `后端 yyy`（须等 07 的哪个分支落地，即接口就绪前提）。**后端未落地时的通行做法**：按 02 的接口定义先行实现、字段做容错（如分页列表名同时兼容 `list` / `records` / `items`），后端定稿后再收紧 —— `feat/mp-medicine` 即是如此落地（见其"落地"行）。联调与回归用 `medbox-miniapp/tools/mock`（`npm run mock` 起假后端、`npm run test:e2e` 端到端自测），**AI 每个功能分支完工时在单元测试后自动跑一遍**（见 `AGENTS.md` 3.1）。
>
> **反过来查"我做完谁能动"**：以本清单各分支的依赖列为准（正向事实源在 `07` / `02` 接口定义），`07` 不再维护反向索引（见 `07` 顶部说明）。

> **路径与分支**：本清单所有代码**都在 `medbox-miniapp/` 下**（如 `src/config/index.js` = `medbox-miniapp/src/config/index.js`）；分支名 `feat/mp-xxx`，**一个分支只改 `medbox-miniapp/`**。文档改动（`medbox-spec/`）与代码放进**同一个 PR** 即可，**不要求同一个 commit**（按层分批提交也可以）。
