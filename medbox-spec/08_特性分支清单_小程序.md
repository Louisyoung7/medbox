# 08 · 特性分支清单（uni-app 小程序）

> 每个 `- [ ]` 待办 **对应一个特性分支**，分支名见每条的 `feat/xxx`。
> **修 Bug、重构项目结构不计入本清单**。
> 图例：🧱 = **地基**；🔧 = **功能任务**；🧭 = **判定型**（含业务规则与优先级，**动手前先出规则表给用户确认**，见 `AGENTS.md` 的 3.1）。
> **认领与引用一律用分支名**（如"对应 08 的 `feat/mp-plan`"），**不要用"第 N 项"** —— 清单会重排，序号不稳定。
> 老人端与监护端（子女 / 护理 / 医生）的视图差异，在各功能分支内按 02 的 1.3 权限规则处理，不单开分支。
> 完成后勾选 `- [x]`，PR 描述写明"对应 08 的 `feat/xxx`"。

> **清单即实施顺序**：第一章地基 → 第二章 **P0 主干闭环** → 第三章 **P1 完善** → 第四章 **P2 锦上添花（可砍）**。
> **本端受后端接口约束**：后端 P0 未落地的接口，对应页面无法联调。因此顺序基本跟随 `07`，只有 `mp-ui-kit`（纯 UI，不依赖后端）可以提前做。
> 已按此原则**合并同类分支**：原 38 个待办合并为 **23 个分支**（见各条括号内的"原待办"）。

> **路径与分支**：本清单所有代码**都在 `medbox-miniapp/` 下**（如 `src/config/index.js` = `medbox-miniapp/src/config/index.js`）；分支名 `feat/mp-xxx`，**一个分支只改 `medbox-miniapp/`**。文档改动（`medbox-spec/`）与代码放进**同一个 PR** 即可，**不要求同一个 commit**（按层分批提交也可以）。

## 一、地基（🧱）

> **工程约定（V1.10 起）**：`medbox-miniapp/` 为 uni-app 官方 CLI 脚手架工程（Vue 3 + Vite 5，`npm run dev:mp-weixin` 出产物到 `dist/dev/mp-weixin`），**独立构建，仓库根没有统一构建脚本**；`.gitignore` **由仓库根统一维护**，端目录不再单独放（见 01 的 4.0）；本地 IP 只写不入库的 `.env.local`，模板为 `.env.example`。

- [x] 🧱 **`feat/mp-auth`** 登录注册与 token 管理
  - 依赖：`mp-request`
  - 参考：02 第 3 章
  - 内容：登录 / 注册页；token 与 refreshToken 本地存储；刷新与过期处理；路由守卫（未登录跳登录页）
  - 验收：账号密码登录成功进首页；token 过期自动刷新
  - **落地约定（后续分支遵守）**：
    - **登录态编排层 `src/store/auth.js`**：`login` / `register` / `logout` / `refreshAuth` / `restoreSession` / `isLoggedIn` / `setupAuth` / `navigateAfterLogin`；页面**只调它**，不要自己拼"写 token + 拉 `/users/me`"
    - **`src/store/token.js` 仍是 token 的唯一读写入口**，用户资料在 `src/store/user.js`（`getUserInfo` / `getRole` / `roleLabel`），路由守卫在 `src/store/guard.js`（白名单 + `redirect` 回跳）—— 三者由 auth.js 统一编排，**不存在第二份 token**
    - **刷新只有"被动"一种**：业务请求 40101 → 请求层交处理器 → `/auth/refresh` → 成功则**自动重发一次原请求**（页面无感知），并发只刷一次；失败才清凭据跳登录。不要另写主动刷新 / 定时刷新
    - **新建页面要进 `src/store/guard.js` 的白名单**，否则未登录时会被守卫挡住；`LOGIN_PATH`（`/pages/auth/login`）改了要同步改白名单与 `src/pages.json`
