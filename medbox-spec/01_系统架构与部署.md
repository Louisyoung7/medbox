# 01 · 系统架构与部署

> 协议：HTTP REST、MQTT（EMQX）、WebSocket　|　通信：局域网（内网）　|　版本见 `CHANGELOG.md`

## 1. 项目背景与功能范围

面向居家养老场景的家用智能药品箱管理系统：设备端以**药箱主控（单片机 / 嵌入式网关）**为核心，负责定时提醒、人机交互与无线通信，并通过 WiFi 挂接**摄像头（药品识别）与温湿度、光照等传感器子设备**；药箱**不划分仓位 / 格子**，药品按"药箱 + 药品"维度管理；云端由 Java 后端（Spring Boot）承载业务；用户侧为 uni-app 小程序，分老人本人端与子女 / 社区护理人员 / 家庭医生的远程监护端。平台管理员不在小程序角色体系内，使用独立 Web 后台。

覆盖 8 项核心功能：

- 按时提醒服药；
- 服药时按剂量（计量）提醒；
- 监测是否拿错药物（错服识别）；
- 监测药物是否过期，过期及时上报；
- 监测是否按时服药，未按时服药上报（漏服）；
- 信息互通（本地端与远程监护端数据 / 告警同步）；
- 存储环境监测（温度、湿度、光照）；
- 接入 AI 大模型，支持药品是否过期、服用禁忌等随时询问。

## 2. 系统架构与协议分工

| 协议 | 链路 | 承载内容 |
|------|------|----------|
| HTTP / REST | 小程序 ⇄ 后端 | 登录鉴权、账号 / 设备 / 药品 / 计划增删改查、历史与统计查询、AI 问答 |
| MQTT（EMQX） | 设备 ⇄ 后端 | 设备遥测上报、服药 / 错服 / 异常事件上报、云端下行（下发计划、触发提醒、控制命令）。摄像头识别结果**经单片机聚合后**在此通道上报 |
| HTTP（图片上传） | 摄像头 → 后端 | 服药抓拍图片上传，**当前为全量上传（正常服药也拍）**，multipart 直传，不过 MQTT、不过单片机（见 5.2） |
| WebSocket | 后端 → 小程序 | 告警实时推送、设备在线状态、实时监测看板 |

MQTT 消息中间件统一使用 **EMQX**（局域网内网部署，详见第 4 章与文档 03）。

## 3. 角色与权限模型

采用 RBAC + 数据归属双重控制。**小程序侧角色**与核心权限：

| 角色 | 说明 | 关键权限 |
|------|------|----------|
| 老人本人 | 设备近场使用者 | 查看本人服药计划、AI 询问、本地查看 |
| 监护人 / 子女 | 远程监护端 | 绑定老人、查看老人全部数据、配置计划与阈值、**为老人配置大模型 API Key**、接收告警 |
| 社区护理人员 | 机构监护端 | 批量管理所辖老人、处理 / 确认告警、导出记录 |
| 家庭医生 | 专业端 | 制定用药方案（计划）、查看依从性报告、维护药品禁忌知识库 |
| 设备端 | 药箱主控 / 传感器 / 摄像头 | 走 **MQTT**（上报遥测 / 事件、接收下行命令）+ **HTTP**（摄像头上传抓拍图片），不参与小程序角色体系 |

**权限原则**：所有查询 / 操作以"当前登录用户对目标老人 / 设备是否具有监护或管理关系"为校验依据，越权返回 40301。

**权限默认规则**（接口级细则见文档 02 的 1.3）：

| 角色 | 默认权限 |
|------|----------|
| 老人本人 | 只读本人数据（计划 / 记录 / 告警 / 设备状态）、AI 问答 |
| 监护人 / 子女 | 对已生效监护关系下的老人**可读可写**（计划、药品、库存、告警处理、阈值、AI Key） |
| 社区护理人员 | 所辖老人只读 + **处理告警** + **导出记录** |
| 家庭医生 | **制定 / 修改服药计划** + **维护药品禁忌知识库** + 查看依从性报告 |

监护关系为**两步生效**：监护人发起申请（PENDING）→ 老人端确认（ACTIVE）；未确认前访问该老人数据返回 40302。校验顺序：登录 → 监护关系 → 关系是否生效 → 该角色是否具备此操作权限。

**平台管理员**：设备准入审核、字典与阈值模板维护等运营职责**不在小程序角色体系内**，由后续设计的 **Web 管理后台** 承载，拥有独立账号体系与鉴权方式（分支清单见 `09`，本期只做「测试数据清理」dev/QA 工具、首个分支 `feat/admin-testdata-cleanup`；管理员接口契约见 `02` 第 10 章）。本文档集所列 REST / MQTT / WS 接口仅面向小程序端与设备端，管理员相关接口不在范围内。凡涉及管理员的操作（如设备准入审核）在 Web 后台完成，小程序端至多发起申请或查看状态。

## 4. 局域网（内网）部署与地址规划

当前阶段系统全部通信均在同一局域网（同一子网）内完成，暂无公网域名与公网 IP：设备、Java 后端、EMQX 与 uni-app 小程序均部署 / 接入同一内网。所有接口路径不变，仅将"域名"替换为"内网 IP + 端口"。

### 4.0 仓库与目录结构（单仓多目录）

后端、小程序与 Web 前端同在**一个仓库 `medbox`**，只靠目录区分；文档也在同一仓库的 `medbox-spec/` 下（**不用 git subtree**，见文档 00）。

```
medbox/
├── AGENTS.md         # 给 AI 助手的工作约定（根目录真实文件，AI 工具自动加载）
├── README.md         # 目录结构与文档入口
├── medbox-server/    # Java 后端（Spring Boot 4 / Java 21 / Gradle） ← 任务清单 medbox-spec/07
├── medbox-miniapp/   # uni-app 小程序（Vue3 + Vite）                ← 任务清单 medbox-spec/08
├── medbox-admin/     # Web 前端 / 管理后台 —— 本期先做「测试数据清理」dev/QA 工具，分支清单见 09
└── medbox-spec/      # 接口与设计文档（唯一权威副本）
```

约定：

1. **各端独立构建、独立依赖**：后端用 Gradle（`./gradlew build`），小程序 / Web 前端各自 `npm ci`；**没有根目录统一构建脚本**，不引入 npm workspaces / Gradle 多项目聚合等额外复杂度（项目不长期维护）。
2. **`.gitignore` 仓库根汇总**：后端 `build/` `.gradle/`、小程序 `node_modules/` `unpackage/` `dist/` `.env.local`、后端本地配置 `application-local.yml` 等，各端不再单独维护。

### 4.1 服务地址与端口规划

各服务地址集中在后端配置（`application.yml`）与小程序端统一配置（`BASE_URL` / `WS_URL`）中，换 IP 时一处修改、全局生效。入库配置不含任何 IP，本机差异经不入库的本地文件覆盖（见 4.1.1 / 4.2）。下表 IP 以 192.168.1.10 为例：

| 服务 | 协议 / 端口 | 内网地址示例 | 备注 |
|------|-------------|--------------|------|
| Java 后端 (REST) | HTTP / 8080 | `http://192.168.1.10:8080/medbox/api/v1` | 默认明文 |
| WebSocket 推送 | WS / 8080（同后端不同路径） | `ws://192.168.1.10:8080/medbox/ws` | 亦可独立端口 8081 |
| MQTT Broker（EMQX） | TCP / 1883 | `tcp://192.168.1.10:1883` | **仅设备端与后端使用**；EMQX Dashboard：`http://192.168.1.10:18083` |
| Web 前端 `medbox-admin`（Vite dev） | HTTP / 5173 | `http://192.168.1.10:5173` | ⏸ **本期仅 `feat/admin-testdata-cleanup`**（测试数据清理工具，分支清单见 `09`）；其余管理功能待定；需后端放行 CORS 或用 dev proxy（见 4.0） |

> **小程序不直连 MQTT**：按第 2 章的协议分工，MQTT 只用于"设备 ⇄ 后端"，小程序侧**只有 `BASE_URL` 与 `WS_URL` 两个地址**，不需要也不配置 `MQTT_URL`。设备上报由后端消费后经 WebSocket 推给小程序；小程序下发的计划 / 命令走 HTTP，由后端转 MQTT 下行。EMQX 无需开启 WebSocket 监听器。

> **出网范围**：公网大模型 API（Chat 问答）属"后端出网"方向，需为后端主机放行到模型域名的出网访问；这与上述内网寻址相互独立。**OCR 与 Embedding 已本地化，不出网、不需要 Key**（详见文档 05 第 4 章）。

#### 4.1.1 后端配置文件：application.yml

`medbox-server/src/main/resources/application.yml` **入库**，不含任何内网 IP（DB / EMQX 连 `localhost`，本机对外 IP 经环境变量 `MEDBOX_HOST` 取）。本地个性化配置写在**不入库**的 `application-local.yml`（`spring.profiles.active=local`）覆盖默认值，不提交。

#### 4.1.2 本地数据库：PostgreSQL 17 + pgvector

结构化数据与说明书向量**同库存放**（文档 06），本地一套 **PostgreSQL 17 + pgvector** 即可，镜像 `pgvector/pgvector:pg17`，端口 5432。建表由 **Flyway** 自动执行（`db/migration/` 下：`V1` 建扩展 + 15 张表 + 索引，`V2` 建 `drug_manual_chunk` 的 HNSW 索引），无需手动建表。

### 4.2 uni-app 小程序端配置注意

- **地址可配置、禁止写死 IP**：`BASE_URL`（`…/medbox/api/v1`）与 `WS_URL`（`…/medbox/ws`）由 `medbox-miniapp/src/config/index.js` 统一构造；HOST 取自不入库的 `.env.local`（`VITE_SERVER_HOST`）或运行时缓存，TLS 开关 `VITE_TLS` 放**入库**的 `.env`（与构建模式无关，`uni build` 是 production 读不到 `.env.development`）。
- **小程序不直连 MQTT**，只有 `BASE_URL` / `WS_URL` 两个地址。
- **微信开发者工具**勾选"不校验合法域名"才能跑 http/ws；真机调试用开发版模式忽略域名校验或走 App 端。**正式上线**需已备案域名 + HTTPS/WSS。
- **两人分别开发**：各人在 `.env.local` 填自己 IP（互不干扰）；`manifest.json` 的 `mp-weixin.appid` 两人**共用同一 AppID** 入库，避免 pull 冲突；个人本地设置（`project.private.config.json`）与 `.env.local`、`application-local.yml` 一并加入仓库根 `.gitignore`。
- 本阶段不做微信登录，后端无需 `appSecret`（AppID 仅用于开发者工具与真机调试，见 02 第 3 章）。

## 5. 关键业务流程串联

### 5.1 按时服药与漏服告警
后端将 MedPlan（含多种药品的 `items`）经 MQTT down/schedule 同步到设备 → 设备到点蜂鸣提醒并等待取药 → 用户在容忍时长内**按 items 逐种取到正确药品**（由摄像头识别药品，不比对仓位），每取一种上报一次 up/event/dispense（onTime=true）→ 后端按 item 写 MedRecord。若容忍时长内**任一 item 无对应上报**，后端定时任务判定生成 MISS 告警（message 列出缺哪几种药），落 Alarm 并经 WebSocket 推送监护端。

### 5.2 错服识别（摄像头）
**药箱不划分仓位，是否拿对药靠摄像头识别药品**：摄像头识别实际取出的是哪种药 → 结果经 WiFi 交单片机 → 单片机聚合后由 `up/event/dispense` 上报：**识别结果与计划药品明确不符 → `wrongDrug=true`**，后端生成 WRONG_DRUG 告警、本地即时声光告警、推送远程监护端；**置信度低于阈值不判错服**（避免误报），抓拍标为 `LOW_CONFIDENCE` 供监护人人工复核。抓拍图片经 HTTP 直传后端留证（已读 7 天 / 未读 30 天，监护人可在小程序查看）。

### 5.3 过期监测与上报
**有效期来自人工录入**，不做标签 / RFID / 图像识别：监护人录入库存或补药入库时手动填写 `productionDate` 与 `expiryDate`（见文档 06 的 2.5）。后端定时按 `medicine_stock.expiry_date` 扫描：临期按 `alarm-settings` 提前期预警、到期生成 EXPIRED 告警并禁止该药品加入服药计划；AI 侧同步库存有效期以回答"是否过期"。

### 5.4 环境超标
**传感器是药箱下的子设备**（温湿度 / 光照等各自有 `device_id`），数据由主控（唯一 MQTT 连接）统一转发，消息中带 `sensorId` 标明来源；**子设备没有 MQTT 连接与遗嘱**，其在线状态由主控通过 `up/sensor/heartbeat` 周期汇总上报 → 后端按**该老人 `alarm_setting.env_threshold`**（温湿光上下限，老人级统一配置，不按药品细分）判定 → 越界生成 ENV 告警并推送；小程序经环境监测接口按传感器拉取曲线展示。

### 5.5 AI 药品问答（含过期咨询）
小程序 POST /ai/chat（携带 elderId）→ 后端校验问答权限，按 elderId 取出监护人配置好的大模型 Key → 拼装库存有效期 + 药品禁忌知识库为上下文 → Java 直连大模型 → 返回带 disclaimer 的回答并落会话记录（详见文档 05）。
